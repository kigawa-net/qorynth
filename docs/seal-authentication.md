# seal 認証・資格情報設計 — Qorynth

> **状態:** 設計案（認証・資格情報の選定と、threshold-crypto §5.1 残課題の具体化）
> **対象:** `qorynth-seal` を中心とする全経路の認証・認可・資格情報（証明書基盤、承認端末、失効）
> **関連:** [設計概要](design-overview.md) / [アーキテクチャ](architecture.md) / [開発計画](development-plan.md)（フェーズ2・3・4・6） / [閾値暗号プロトコル選定](threshold-crypto.md)（§4・§5） / [OpenBao 連携方式](openbao-integration.md)（§4） / [P2P 通信層設計](p2p-transport.md)（§5）

本書は、threshold-crypto §5.1 が「seal の認証・資格情報設計で閉じる必要がある」と残した課題 —— **1台＋1台盗難の場合、盗難機器がオンライン化され `qorynth-seal` に Unwrap を要求する経路** —— を閉じる。あわせて、openbao-integration §4 と p2p-transport §5 に分散している認証の記述を一本の設計に統合し、両書が「フェーズ2に委ねる」「要確定」とした項目（CA 構成、証明書の有効期間・更新・失効、ロールの表現方式）を決める。

実装コードは含まない。**認証情報・秘密値も含まない**（`<cluster>`、`<node_id>` などのプレースホルダのみ）。

> **開発計画との対応（注意）**
> 認証の実装は、ノード認証・CA・メンバーシップ＝フェーズ2、承認端末＝フェーズ3、状態管理（LOCKED/ACTIVE と全台再起動）＝フェーズ4、seal の Transit 互換ファサードと Bao 認証＝フェーズ6 に分かれる。本書はそれらを横断する設計であり、各節の末尾（§6.5）に対応表を置く。

> **確認状況（重要）**
> WebAuthn・TPM 2.0・X.509 に関する記述は執筆時点の知識に基づく。OpenBao の Transit Seal が実際に送る認証ヘッダや API の集合は、openbao-integration §6.1 のスパイクで確定する。確証のない箇所には **【要確認】** を付けた。

## 0. 要約

| 項目 | 結論 |
|---|---|
| 一次資格情報 | **X.509 証明書による mTLS（TLS 1.3）**。ノード・seal・signal の秘密鍵は **TPM 内の非エクスポート鍵**。OpenBao（Bao）クライアント鍵のみ OpenBao の仕様上ファイルとなる（§2.4） |
| 認可の根拠 | 証明書チェーンではなく、**Raft 上の許可リスト（公開鍵ハッシュ＝`node_id` への固定）**。CA が漏れても、許可リストに載らない証明書は何も許可されない（§4.1） |
| トークン | **認証には使わない**。例外は OpenBao Transit Seal の互換のためだけに置く不透明トークンで、**単独では何も許可しない**（§2.3） |
| 承認端末 | **WebAuthn（ES256、User Verification 必須、端末固定資格情報）**。承認は、ノードが**自分で検証できる承認証明書**（WebAuthn assertion の束）として Raft に入る。Signaling・approval サービスは信頼点にしない（§5） |
| CA 構成 | **オフライン Root CA → ロール別の中間 CA**（node / seal / bao / signal / admin）。発行は承認付きのオフライン儀式（`qorynth` CLI＋ハードウェアトークン）。Root と中間は信頼の分離単位（§3） |
| 失効 | **Raft への失効エントリが一次手段**（CRL/OCSP は使わない）。コミット適用と同時に新規接続拒否＋既存接続の強制切断。証明書の短い有効期限は二次の保険（§3.4） |
| 残課題の閉め方 | 盗難ノードの Unwrap 要求を、**ロール別リスナー分離 → 許可リスト → 接続元固定 → ノード側の暗号文登録照合 → Bao `sealed` 状態突合 → 通知 → 非対称キルスイッチ**の順に、すべて fail-closed で拒否する（§4.4）。**盗難 Bao を元の場所・元の状態で再接続された場合は暗号的には閉じられない**ことを明記し、検知＋即時失効＋段階的ゲートで閉じる |
| 承認の段階 | **ロック=1台 / 隔離=2-of-5 / 有効化・追加・Resharing=3-of-5 / 端末集合の変更=4-of-5 または復旧管理者鍵**（§5.3）。端末3台盗難でも端末集合は書き換えられない |

## 1. 認証モデルの全体像

### 1.1 認証が必要な経路

| # | 経路 | 方向 | プロトコル | 認証の主体 | 備考 |
|---|---|---|---|---|---|
| P1 | OpenBao → `qorynth-seal`（Unwrap / Wrap 要求） | Bao がクライアント | HTTPS（HTTP/2, TLS 1.3, mTLS） | Bao ノードごとの証明書 | Transit Seal 互換ファサード（openbao-integration §2.3）。本書の中心 |
| P2 | `qorynth-seal` → `qorynth-node`（部分復号要求） | seal がクライアント | QUIC / TLS 1.3 mTLS、ALPN `qorynth-decrypt/1` | seal 証明書（`seal` ロール）とノード証明書 | 双方向に検証。部分復号を要求できるのは `seal` ロールのみ |
| P3 | `qorynth-node` ↔ `qorynth-node`（Raft・DKG・Resharing） | 対等 | QUIC / TLS 1.3 mTLS | ノード証明書（`node` ロール）＋ TPM | Share は送らない（sub-share のみ HPKE で宛先暗号化） |
| P4 | `qorynth-seal` → OpenBao（`seal-status` 参照） | seal がクライアント | HTTPS（サーバ検証のみ） | OpenBao のサーバ証明書 | 無認証・読み取り専用（L4 突合用） |
| P5 | `qorynth-signal` ↔ `qorynth-signal` / ノード → signal | — | QUIC / TLS 1.3 mTLS | signal / node 証明書 | Signaling は信頼点ではない（p2p-transport §3.2） |
| P6 | 承認端末 → signal（承認口）→ ノード | 端末がクライアント | HTTPS/WSS（Web PKI）＋ WebAuthn | 端末の WebAuthn 資格情報 | signal は承認の**転送のみ**。検証はノード（§5） |
| P7 | `qorynth` CLI → ノード / seal（管理操作） | CLI がクライアント | QUIC mTLS | `admin` ロール証明書＋**操作ごとの承認証明書** | 証明書だけでは特権操作は不可（§1.3） |
| P8 | CA 儀式（証明書発行・Root/中間の保管） | オフライン | 非ネットワーク | ハードウェアトークン＋承認証明書 | §3 |

> **P2 の補足:** 本書では **seal が常にダイヤル側**（pull 型）とし、**ノード → seal 方向の接続は設けない**。seal のリスナーは P1（Bao 向け）と、ローカルの監視口のみ。ノードが seal へ来る経路を持たないため、盗難ノードが seal に接続しても受け付けるリスナーが存在しない（§4.3）。

### 1.2 各経路の認証要件

| 経路 | 必須の認証要素 | 認可（認証後の判定） | 通信路で満たすべき性質 |
|---|---|---|---|
| P1 | mTLS（`bao` ロール証明書）＋許可リスト照合＋（互換用）不透明トークン | Bao ノード ID × `key_id` × 操作（encrypt/decrypt）× 接続元アドレス × レート。**L3〜L6 のゲート** | TLS 1.3 必須。サーバ検証は Bao 側が CA ピン留め。`tls_skip_verify` 禁止 |
| P2 | 双方向 mTLS。seal は `seal` ロール、ノードは `node` ロールとして相互に検証 | ノード側で `seal` ロール・クラスタ `ACTIVE`・`SHARE_LOADED`・`epoch`・暗号文登録・用途・レート | 0-RTT 禁止（リプレイ防止） |
| P3 | mTLS＋TPM ＋ Raft メンバーシップ照合 | `node_id` が現行メンバーかつ非失効 | 失効時に既存接続も再評価・強制切断 |
| P5 | mTLS＋チェーン検証 | ロール一致・許可リスト（signal は可用性のみ。ベストエフォート） | — |
| P6 | WebAuthn assertion（UV 必須）。ノードが独立に検証 | 承認種別ごとの閾値・端末集合の版・有効期限・ワンタイム nonce | 通信路は Web PKI だが、**完全性・真正性は assertion が担保**（通信路を信頼しない） |
| P7 | mTLS（`admin`）＋承認証明書 | 操作の種別ごとの承認段階（§5.3） | — |

共通原則:

1. **認証（誰か）と認可（何をしてよいか）を分ける。** 認証は証明書（TLS ハンドシェイク）、認可は Raft の許可リストと承認証明書。
2. **fail-closed。** 許可リスト・クラスタ状態・承認証明書のいずれかを判定できない（古い、検証不能）場合は拒否する。可用性より機密性を優先するのは「許可」方向のみで、「拒否」方向の操作（ロック・隔離）は逆に軽く・速くする（§5.3）。
3. **ロールで経路を分離する。** 証明書の SAN URI（`qorynth://<cluster>/<role>/<id>`）のロールと、リスナー・ALPN を一対一に対応させる。あるロールの証明書で他ロールのリスナーに入れない。
4. **Signaling・承認サービス・ロードバランサを信頼点にしない。** 通信の仲介役は可用性にしか影響しない（p2p-transport §3.2）。
5. **許可方向の変更はすべて承認付き。** 許可リストへの追加・復活は承認証明書なしにはコミットできない（§4.1・§5）。

### 1.3 信頼の構造（何が何を縛るか）

```
復旧管理者鍵（オフライン M-of-N）  ┐
承認端末（3-of-5 / 4-of-5）        ├─►  Raft 上の AuthRegistry（許可リスト・端末集合・信頼アンカー）
Root CA（オフライン）              ┘          │ 各エントリは承認証明書つきでのみ適用される
                                              ▼
                  ┌───────────────┬──────────────────────┐
              ノード認可      seal / bao / signal 認可   承認端末認可
```

- **信頼の源泉は「Raft の AuthRegistry」**。CA は証明書の形式検証（有効期間・EKU・チェーン）を担う補助的な層で、**認可を単独では決めない**。
- AuthRegistry の書き込みは、承認証明書の検証に通ったエントリだけが**状態機械の適用関数**で受理される（§4.1）。Raft のリーダーが侵害されても、承認のないエントリは他ノードが適用しない。

## 2. 資格情報の選定

### 2.1 比較

| 観点 | **X.509 証明書（mTLS）** | 署名付きトークン（JWT/PASETO/Macaroon など） | 共有シークレット（API キー・パスワード） |
|---|---|---|---|
| 所持の証明 | 秘密鍵の所持を TLS ハンドシェイクで毎接続証明する | 発行後は Bearer。盗まれたらそのまま使える（バインドしない限り） | Bearer。漏れたら誰でも使える |
| 鍵のハードウェア保護 | TPM / HSM の非エクスポート鍵を TLS に直接使える | 署名鍵は保護できても、トークン自体は保護できない | 保護不能（値そのものが資格情報） |
| 失効 | 許可リスト（Raft）で即時。CRL/OCSP に依存しなくてよい | 短い有効期限＋失効リスト。期限内の失効が課題 | ローテーション（全クライアント更新） |
| 通信路との結合 | TLS 終端と同じ層（チャネルバインド不要） | 別層。チャネルと結合しないと盗用可 | 同上 |
| 運用コスト | CA が必要。発行・更新の運用が要る | 発行機構（STS）が必要。ここでは増える | 最も軽い |
| ライブラリ・互換 | QUIC・HTTP/2・OpenBao Transit Seal が標準対応 | Transit Seal は `X-Vault-Token` の不透明値のみ | 同左 |
| **本システムとの適合** | ◎ P1〜P5・P7 | △ 承認の束ね役（§5）には構造体として使うが、Bearer としては使わない | ✕ 単独では使わない |

### 2.2 推奨方式と理由

> **一次資格情報は X.509 証明書（mTLS, TLS 1.3, ECDSA P-256）。**
> **認可は Raft 上の許可リスト（公開鍵固定）。承認は WebAuthn assertion の束（承認証明書）。**
> **Bearer トークンと共有シークレットは、認証手段として採用しない。**

理由:

1. **鍵の所持が毎接続で証明され、盗用に強い。** ノード・seal・signal の秘密鍵は TPM 内の非エクスポート鍵にできるため、ディスクの複製だけでは資格情報が持ち出せない（利用できるのは「その機械の上」のみ。この限界は §7 で明示する）。Bearer 方式は値の複製がそのまま攻撃成立になる。
2. **既存設計と一貫する。** p2p-transport（QUIC + mTLS、`node_id` ＝ 公開鍵ハッシュ）・TPM 2.0 ノード ID・P-256 の暗号スイート（threshold-crypto §1.4）と同じ鍵型で統一でき、WebAuthn（ES256）とも揃う。
3. **失効を Raft で即時に効かせられる。** 認可の根拠を「公開鍵ハッシュの許可リスト」に置くため、CRL/OCSP の配布遅延や、OCSP 応答者という新たな可用性依存を持ち込まない（p2p-transport R8）。
4. **OpenBao を無改造で接続できる。** Transit Seal はクライアント証明書（ファイルパス指定）と TLS 設定を受け付ける【要確認: 版ごとの設定項目】。mTLS は Bao 側設定が「証明書パス」だけで済む（openbao-integration §4.2）。

### 2.3 トークンの扱い（例外を一つに限定する）

| 用途 | 扱い |
|---|---|
| OpenBao Transit Seal 互換（`X-Vault-Token` 相当） | Bao の設定上の都合で置く**不透明なランダム値**（256 bit）。seal は **ハッシュ（SHA-256）のみ**を許可リストに保持し、定数時間比較する。高エントロピーなのでパスワード用ハッシュ（Argon2 等）は不要。**これ単独では何も許可しない**（mTLS の ID と許可リスト一致が前提）。値の受け渡しは環境変数・シークレットファイル（リポジトリ・設定本体・ログに平文を置かない） |
| 内部通信のアクセストークン（OAuth 風） | **採用しない** |
| 承認 | トークンではなく **承認証明書**（WebAuthn assertion の束、§5.2）。ノードが検証する |
| 許可リストのスナップショット（seal 配布用） | 署名付き構造体（§4.4）。Bearer ではなく、**検証側が署名と鮮度を確認する**公開データ |

**率直な位置づけ:** Bao 側では証明書の秘密鍵もトークンもファイルとして同じホストに置かれる。したがってトークンは**独立した第二要素にならない**。目的は、(a) Transit Seal の仕様互換、(b) 許可リストの操作ミス・誤配線（別サービスからの誤接続）の検出、(c) ローテーションを許可リスト更新と同時に行うことでの資格情報の世代管理、に限られる。盗難対策としての期待はしない（その役割は §4.4 の多層防御）。

### 2.4 資格情報の保管場所

| 主体 | 資格情報 | 保管 | 備考 |
|---|---|---|---|
| `qorynth-node` | TLS 鍵（`node` ロール）| **TPM 内の非エクスポート鍵**（`fixedTPM` / `fixedParent`、PCR ポリシー付き） | 署名操作は 1 ハンドシェイクごとに TPM を使う（数十〜数百 ms。p2p-transport §7）。接続は使い回す |
| `qorynth-seal` | **鍵を用途で分ける**: (a) Bao 向けサーバ鍵、(b) ノード向けクライアント鍵（`seal` ロール） | 両方 TPM。(a) と (b) は**別の鍵・別の証明書** | (a) は Bao 側の攻撃面に晒されるため、侵害が (b)＝Unwrap 権限へ波及しないよう分離 |
| `qorynth-signal` | TLS 鍵（`signal` ロール）＋承認口の Web PKI 用サーバ鍵 | TPM（可能なら）。承認口は別リスナー・別鍵 | 承認口の鍵は Web PKI（ACME 等）で管理 |
| OpenBao ノード | クライアント鍵（`bao` ロール）＋トークン | **ファイル**（ファイル権限＋ディスク暗号化）。OpenBao がファイルパスで受け取る仕様のため TPM 直接利用不可【要確認】 | 強化案: Bao ホストにローカル TLS プロキシ（TPM 鍵）を置く（§8.2） |
| 承認端末 | WebAuthn 資格情報 | 端末のセキュアエレメント／プラットフォーム認証器（端末固定） | §5.1 |
| CA | Root 鍵・中間鍵 | **別々のハードウェアトークン**（PIV/HSM 相当）。Root はオフライン | §3 |
| 復旧管理者 | 復旧管理者鍵（M-of-N 署名の各鍵） | 各自のハードウェアトークン | §5.3 |

TPM が守るのは「**秘密鍵の複製**」であって「盗難機器の現地利用」ではない。盗難された機械が同じソフトウェア状態で起動できる場合、TPM 鍵はその機械の上でなお使える。したがって 1 台盗難の防御の本体は閾値暗号（threshold-crypto §5.1）と、本書の失効・ゲートである。

## 3. 証明書基盤（CA）の設計

### 3.1 CA 構成

> **推奨: オフライン Root CA ＋ ロール別の中間 CA。発行は承認付きのオフライン儀式（`qorynth` CLI ＋ハードウェアトークン）。固定された常時稼働の CA サーバーは置かない。**

```
 Root CA（オフライン・ハードウェアトークン・自己署名・長寿命）
   ├─ node-ca      … `node` ロール証明書（Qorynth ノード）
   ├─ seal-ca      … `seal` ロール（ノード向けクライアント）＋ seal の Bao 向けサーバ証明書
   ├─ bao-ca       … `bao` ロール（OpenBao クライアント）
   ├─ signal-ca    … `signal` ロール
   └─ admin-ca     … `admin` ロール（CLI 運用者）
```

| 項目 | 方針 | 理由 |
|---|---|---|
| ロール別中間 CA | 上記 5 本。それぞれ **別の鍵・別のトークン**で保管する | 漏えい時の影響をロール単位に閉じる。**Bao が CA ピン留めするのは `seal-ca` のみ**とし、他ロールの CA 漏えいが Bao ↔ seal の MITM に波及しないようにする（§7.3） |
| ロールの表現 | **SAN URI（`qorynth://<cluster>/<role>/<id>`）＋「発行元の中間 CA」** の二重 | p2p-transport §5.2 が未確定とした「SAN URI か別 CA か」への回答。**検証側は、SAN のロールと発行元中間 CA の対応を必ず確認**する |
| `node_id` | 証明書の SubjectPublicKeyInfo の SHA-256（p2p-transport §5.2 に従う） | 許可リストの固定キー |
| 拡張 | 中間 CA は `pathLen=0`。葉は `clientAuth`／`serverAuth` を役割に応じて限定。`keyUsage` は `digitalSignature` のみ | 誤用の抑制 |
| Name Constraints | **補助にとどめ、検証コード側のロール・クラスタ ID 照合を主とする** | RFC 5280 §4.2.1.10 は URI 制約に **FQDN 形式の host** を要求し、host が FQDN でない URI を持つ証明書を拒否する。`qorynth://<cluster>/…` の `<cluster>` が FQDN でない場合、NameConstraints に頼ると標準実装で拒否され得る。採用するなら `<cluster>` を `<cluster>.qorynth.internal` 形式にする【要確認: 利用する TLS ライブラリの URI SAN・制約の扱い】。いずれにせよ p2p-transport §8.1 のとおり**カスタム検証が必要** |
| DNS SAN | **seal の Bao 向けサーバ証明書のみ**に DNS 名（VIP/LB の名前）を載せる | Bao の TLS がホスト名検証を行うため。他の経路は DNS 名を使わない（p2p-transport §5.2） |
| 鍵型 | ECDSA P-256（TPM 2.0 が標準でサポート） | threshold-crypto・WebAuthn と統一 |
| Root の有効期間 | 10 年（要レビュー） | オフライン保管。更新は信頼アンカーの変更＝最高段階の承認（§5.3） |
| 中間 CA の有効期間 | 2〜3 年 | 儀式でロール別に更新 |
| 葉証明書の有効期間 | **TPM 鍵（node / seal / signal）: 1 年。ファイル鍵（bao / admin）: 90 日** | 失効は Raft が一次手段なので、有効期間は「失効し損ねた資格情報が自然に死ぬ」ための二次の保険。ファイル鍵は複製されやすいので短くする。更新の儀式負荷は §3.3 で束ねる |

### 3.2 証明書の発行（承認付きオフライン儀式）

発行は「**承認証明書を確認した上で、ハードウェアトークンの中間鍵で署名する**」手順とし、常時稼働の発行サーバーを持たない（「固定された中央管理ノードなし」の方針、設計概要 §3）。

```
① 申請   新しい主体（ノード／seal／Bao／signal／運用者）が自分の鍵ペアを生成して CSR を作る
           ・ノード／seal／signal: TPM 内で鍵生成。CSR と併せて TPM の証明情報を提出
             （EK 証明書チェーンの検証と、AK による TPM2_Certify で「この鍵は TPM 内の非エクスポート鍵」を確認）【要確認】
           ・Bao / admin: ファイル鍵。TPM 証明は不要（その分、有効期間が短い）
② 承認   該当する承認段階（§5.3）の承認証明書を得る
           承認対象のハッシュ = H(operation=issue, role, SPKI hash, 申請者の識別, 有効期限, key_id/権限) 
③ 署名   `qorynth ca issue`（オフライン端末）が承認証明書を検証 → 該当ロールの中間鍵トークンで署名
           ※ 承認証明書の検証は CLI 側のソフトウェア的な強制であり、トークン自体が承認を暗号的に強制するわけではない
④ 登録   AuthRegistry へ新エントリ（`SPKI hash`・ロール・権限・（Bao は）接続元アドレス）を、
           同じ承認証明書つきで Raft にコミット
⑤ 配布   証明書本体を主体へ渡す（帯域外または CLI 経由）。証明書は公開情報なので配布経路の機密性は不要
```

- **③ の強制力の限界を明記する。** 中間鍵のトークンを持つ者が CLI を迂回すれば、承認なしに証明書の署名自体はできる。ただし**④の AuthRegistry 登録は Raft の適用関数が承認証明書を検証する**ため、承認なしに発行した証明書は許可リストに載らず、認可を得られない（§4.1）。つまり CA 秘密鍵は認可の単一障害点ではない。
- 閾値署名で CA を構成する案（常時稼働しつつ秘密鍵の単一保持者を作らない）は、X.509 の ECDSA 互換が要るため DKLs23 / CGGMP21 を要する。threshold-crypto §3.2 のステップ3（署名）の成果物に依存するため、**将来案**とする（§8.1）。

### 3.3 更新

| 対象 | 周期 | 手順 | 備考 |
|---|---|---|---|
| 葉（TPM 鍵） | 1 年。**期限の 30 日前に更新儀式** | 同じ TPM 鍵（同じ `node_id`）で新しい証明書を発行。**公開鍵が変わらないため許可リスト・`node_id` は不変** | 更新は「同一 SPKI の再発行」なので、承認段階は低め（§5.3 の「更新」）。ただしロール・権限の変更は新規扱い |
| 葉（ファイル鍵: Bao） | 90 日 | 鍵を再生成する場合は新規扱い（新 SPKI → 許可リスト更新）。鍵を使い回す更新は避ける | 鍵ローテーションは許可リスト更新・トークン更新と同時（openbao-integration §4.2-4） |
| 中間 CA | 2〜3 年 | Root が新中間を署名 → 葉を再発行 | 葉の SPKI は不変なので、許可リストは書き換え不要 |
| Root CA | 10 年 | 新 Root を生成 → 信頼アンカーの更新を復旧管理者鍵＋最高段階の承認で AuthRegistry へ → 全員に新チェーンを配布 | 全体手順。発生は稀 |

- **期限切れで止まらないための運用:** 期限の 60/30/14 日前に警告し、更新儀式を前倒しで実施する。**期限切れ証明書の猶予（grace）は設けない**（fail-closed）。時刻は NTP 等で同期し、時刻ずれに備えて監視する（p2p-transport §5.4）。
- 更新儀式の件数は、現行構成では node 3＋seal 2（×2 鍵）＋signal 3＋Bao 3＋admin が数名程度であり、**葉を束ねて 1 回の儀式で処理**できる。将来の自動化は §8.1。

### 3.4 失効（リボケ）の仕組み

> **一次手段: AuthRegistry（Raft）への失効エントリ。二次: 短い有効期限。CRL/OCSP は使わない。**

| 項目 | 内容 |
|---|---|
| 失効の単位 | `SPKI hash`（`node_id` 等）。証明書の再発行でも SPKI が変わらないケースがあるため、**鍵単位で失効**する。ロール＋ID でも指定可 |
| 失効エントリ | `Revoke { role, spki_hash, reason, effective_epoch/seq, approval_cert }` を Raft に追記。**トゥームストーンは葉の最長有効期間（1 年）＋余裕の間保持**し、その後に圧縮する |
| 効力 | **Raft の適用時点で即時**。ノードは (1) 以降の新規接続・新規要求を拒否、(2) **確立済み接続を再評価して強制切断**（TLS のクライアント証明書は接続時にしか検証されないため、継続接続の再検証が必須。p2p-transport §5.4）、(3) 失効した `bao`／`seal` の要求は要求ごとの評価で拒否 |
| seal への伝播 | seal は Raft メンバーではないので、ノードが配る**署名付き許可リストスナップショット**（§4.4 L1）で受け取る。**有効期限（数十秒）を過ぎたスナップショットでは Unwrap を拒否**（fail-closed） |
| signal への伝播 | **ベストエフォート**（p2p-transport §3.4）。signal の失効漏れは認証を破らず（認可はデータ経路の mTLS が決める）、可用性・濫用抑制にしか影響しない |
| 承認段階 | 隔離（deny 方向）は低い段階で即時、復活・再登録は高い段階（§5.3）。**非対称**にして盗難発覚から遮断までの時間を最短にする |
| Raft 多数派が無いとき | 失効を Raft に書けない。**緊急ローカル拒否**（§5.3 の Tier L／S の署名付き deny を、到達可能な各ノード・seal がローカルの拒否リストに即時適用。後で Raft に併合）を用意する |
| 失効の認可基準 | threshold-crypto §6.1 の「失効の認可基準」への回答は §5.3 |

> **CRL/OCSP を使わない理由:** 認可の根拠が Raft の許可リストなので、チェーン上の証明書が有効でも許可リストに載らなければ拒否される。CRL/OCSP は配布遅延・取得失敗時の fail-open/closed の判断・OCSP 応答者の可用性という別の障害点を足すだけで、得られる効果が Raft の失効を超えない。ただし、**Bao が seal のサーバ証明書を検証する側**は OpenBao の TLS 実装に依るため Raft 失効が効かない（§7.3 で扱う）。

### 3.5 配布方法

| 対象 | 方法 |
|---|---|
| Root CA・中間 CA の公開情報（証明書） | `qorynth` CLI で配布（p2p-transport §5.3）。**初回は TOFU に任せず、フィンガープリントを帯域外で確認**。genesis 記録（§6.1）の信頼アンカーとしてハッシュを固定 |
| 葉証明書 | 発行儀式の成果物を主体へ直接渡す。公開情報で、配布の機密性は不要 |
| 秘密鍵 | **配布しない**。主体が自分で生成（TPM 内・または Bao ホスト上）。CA・CLI は秘密鍵を見ない |
| 許可リスト・失効 | Raft（ノード）、署名付きスナップショット（seal）、ベストエフォート（signal）。CA 経由では配布しない |
| Bao 向けに seal-ca を渡す | Bao ホストの設定（CA ピン留め）。**seal-ca の公開証明書のみ**を置く |

## 4. seal 認証の詳細設計

### 4.1 AuthRegistry（認可の源泉）と、承認を適用関数で検証する設計

Raft 上に **AuthRegistry** を置く（Raft ログとして複製され、全ノードが同じ状態を持つ）。

| 領域 | 内容 |
|---|---|
| `genesis` | 初期化儀式の記録のハッシュ。信頼アンカー（Root CA 公開鍵、復旧管理者の公開鍵集合、初期の承認端末集合）を固定 |
| `trust_anchors` | 現行の Root CA・中間 CA の公開鍵ハッシュ（ロール別） |
| `members` | `node` ロールの `node_id`、状態（`LOCKED`/`ACTIVE`/`INVALIDATED`） |
| `seals` | `seal` ロールの `spki_hash`（seal 1・2、クライアント鍵）、権限 |
| `baos` | `bao` ロールの `spki_hash`、**許可される操作・`key_id`・接続元アドレス（/32 など）・レート上限・トークンのハッシュ・状態** |
| `signals` | `signal` ロール |
| `devices` | 承認端末の資格情報（公開鍵・credential ID・AAGUID・所有者ラベル・状態）と**端末集合の版（`device_set_version`）** |
| `ct_registry` | **登録済み暗号文のダイジェスト**（root key クラス。§4.4 L3）。`H(R ‖ info ‖ key_id ‖ key_version)` |
| `revocations` | 失効エントリ（§3.4） |
| `policy` | 承認段階の閾値、有効期限、レート、ゲートの設定 |

**書き込みの規則（中核）:**

1. すべての書き込みエントリは **承認証明書（§5.2）またはロック用の単独 assertion** を添える。
2. **各ノードの状態機械の適用関数が、承認証明書を決定的に検証し、通ったものだけを適用する**。Raft のリーダーが侵害されても、承認のないエントリは他ノードが適用しない（Raft 単体は BFT ではないため、この検証が「1 ノード侵害」への耐性を与える）。
3. 検証は決定的でなければならない。時刻に依存する有効期限は、**リーダーがエントリに記録した提案時刻**を用い、追従側は AppendEntries 時に許容時刻ずれ内であることを確認する【要詳細化】。
4. 端末集合の版・承認の nonce をエントリに含め、**承認の再利用（別操作・別時点での使い回し）を適用関数が拒否**する（§5.2）。

### 4.2 OpenBao → `qorynth-seal` の接続認証（P1）

| # | 項目 | 設計 |
|---|---|---|
| 1 | 一次認証 | **mTLS（TLS 1.3）**。Bao ノードごとの**個別クライアント証明書**。チェーンが `bao-ca` に連なり、SAN URI が `qorynth://<cluster>/bao/<bao_id>`、ロールと発行元 CA が一致すること |
| 2 | 固定 | **SPKI ハッシュ**が `baos` の許可リストと一致すること。CA が同じでも、登録外の証明書は拒否（openbao-integration §4.2-1） |
| 3 | 接続元 | **接続元アドレスが許可リストの登録値と一致**すること（L2/L4 の入力）。L4 LB は **TLS パススルー（L4）**とし、L7 終端でクライアント証明書を失わない構成にする。PROXY プロトコル等でアドレスを渡す場合は、信頼できる LB からの接続に限定する |
| 4 | トークン | 互換用の不透明トークンを定数時間比較（§2.3）。**単独では許可しない** |
| 5 | 権限 | `key_id = openbao-root`（仮称）への `encrypt` と `decrypt` のみ。`rewrap`・`sign`・管理系は不公開 |
| 6 | サーバ側 TLS | seal の Bao 向けサーバ証明書は `seal-ca` 発行。Bao は **`seal-ca` をピン留め**（`tls_skip_verify` 禁止）。鍵は (b) のノード向けクライアント鍵と分離（§2.4） |
| 7 | リスナー分離 | Bao 向けリスナーは **`bao` ロール証明書のみ受理**。`node`・`seal`・`admin` ロールの証明書はハンドシェイク段階で拒否 |
| 8 | 失効 | 要求ごとに許可リスト（スナップショット）を評価。失効の効力は Raft 適用後ただちに（§3.4） |

> **Encrypt（Wrap）経路の注意:** 初期化・migration 時、Bao は **root key の平文を seal に送る**。この瞬間の seal サーバが、Qorynth と Bao の間で最も機密性の高い信頼点になる。(a) この操作は運用者が明示的に開く**ウィンドウ**（openbao-integration §4.4 L3）でのみ許可する、(b) Bao 側の `seal-ca` ピン留めと seal サーバ鍵の TPM 保護、(c) ウィンドウ中の seal サーバ証明書のフィンガープリントを帯域外で確認する、の 3 点で守る。

### 4.3 ノード ↔ seal の接続認証（P2）と、ノード → seal 方向の拒否

**seal → node（部分復号要求）:**

| 項目 | 設計 |
|---|---|
| 相互検証 | seal はノードの**サーバ証明書**（`node-ca`、ロール `node`、`node_id` が現行メンバー）を検証。ノードは seal の**クライアント証明書**（`seal-ca`、ロール `seal`、SPKI が `seals` に登録）を検証 |
| ALPN | `qorynth-decrypt/1`。**`seal` ロールのみ**このハンドラへ到達できる（`node` ロールの Raft 用 ALPN とは別） |
| 追加検証 | seal は部分値の **DLEQ 証明**を `Y_i`（コミットメント由来）で検証（threshold-crypto §2.7）。**偽ノードは正しい証明を作れない**ため、ノード認証が破られても暗号的に検出される |
| 0-RTT | 使わない（リプレイ防止。threshold-crypto §6.2） |
| 要求の中身 | `request_id`・`key_id`・`epoch`・`R`・`info`・`purpose`・**呼び出し元 Bao の識別（監査用）**・短い期限 |

**node → seal（拒否する経路）:**

- seal は**ノード方向のインバウンドを持たない**（§1.1 P2 補足）。seal のリスナーは Bao 向け（`bao` ロールのみ受理）とローカル監視口だけである。
- したがって、盗難されたノードが seal へ接続しようとしても、(1) 受理するリスナーが無い、(2) `bao` リスナーは `node` ロールをハンドシェイクで拒否する、の二重で閉じる。
- 同様に、**盗難ノードが他ノードへ部分復号を要求しても**、`qorynth-decrypt/1` は `seal` ロールしか受け付けないので拒否される（threshold-crypto §5.1）。

### 4.4 Unwrap 要求の認証と、threshold-crypto §5.1 残課題の閉め方

> **課題の再掲:** 認証された Bao ノードは、Auto-Unseal の性質上 root key を得られる。盗難した Bao の資格情報（証明書・トークン・ブロブ）でオンライン化し Unwrap を要求する経路が残る。暗号（閾値）では防げない（`d` は Qorynth 側にあり、seal が正当と判断すれば復号するため）。したがって、**要求の正当性の判定精度**で閉じる（openbao-integration §4.4.1）。

**本書の貢献:** openbao-integration の L0〜L6 を前提に、(i) どこで何を検証するか（seal とノードの役割分担）、(ii) 認証層の具体（リスナー分離・SPKI 固定・接続元固定・署名付きスナップショット・ノード側の暗号文照合）、(iii) 盗難シナリオごとの拒否の行方、(iv) 暗号的に閉じられない領域の明示、を与える。

#### 判定の流れ（すべて fail-closed。いずれかが不成立なら拒否・監査）

```
Bao ──mTLS──► qorynth-seal                                           【seal で判定】
   G1 リスナー/ロール    bao ロール証明書か（node/seal/admin は拒否）
   G2 チェーン・有効期限  bao-ca に連なり、期限内か
   G3 許可リスト         SPKI ハッシュが baos に登録・非失効（スナップショットが新鮮）
   G4 接続元             接続元アドレスが登録値と一致
   G5 トークン           互換トークンのハッシュ一致（補助）
   G6 権限・レート       key_id × 操作が許可内か。per-Bao のレート上限・同時実行
   G7 暗号文クラス       decrypt の対象が ct_registry の登録済みか（未登録は拒否）  ＝ L3
   G8 OpenBao 状態突合   登録アドレスの seal-status が sealed:true か             ＝ L4
   G9 通知              root key クラスの decrypt は毎回運用者へ通知・監査         ＝ L5
        │
        ▼ （G1〜G9 通過後に初めて）
qorynth-seal ──mTLS/QUIC──► qorynth-node ×2〜3                       【ノードで再判定】
   N1 リスナー/ロール    seal ロールか（qorynth-decrypt/1）
   N2 クラスタ状態       ACTIVE か・自ノードが SHARE_LOADED か             ＝ L0
   N3 seal 登録          seal の SPKI が seals に登録・非失効（自分の Raft 適用済み状態）
   N4 暗号文照合         H(R ‖ info ‖ key_id ‖ key_version) が ct_registry にあるか  ★ノード側 L3
   N5 epoch・R の妥当性  現行 epoch・R が曲線上の点（threshold-crypto §2.7）
   N6 ノード側レート     key_id 単位の上限（グローバル）・用途許可リスト
   N7 監査              要求元・key_id・時刻・request_id を追記
        ▼
   D_i と DLEQ 証明を返す
```

#### 各ゲートの設計

| ゲート | 具体 | 閉じるもの |
|---|---|---|
| **G1/N1 ロール別リスナー** | リスナーと ALPN をロールに一対一対応。他ロールの証明書は TLS ハンドシェイクで拒否 | 盗難ノード・盗難 seal の証明書の越権利用（ロール混同） |
| **G3 許可リストの鮮度** | seal はノードが配る**署名付きスナップショット**（`seq`・`valid_until`・許可リスト一式・**2 ノード以上の署名**）を保持。数秒〜十数秒ごとに更新。`valid_until`（数十秒）を過ぎたら Unwrap を拒否。署名者は `members` の現行ノード（署名鍵はノードの TLS 鍵と別の署名専用鍵）【要確認】 | 失効後も古い許可リストで通す攻撃。**Unwrap にはどのみちノード 2 台が要る**ため、鮮度の維持は可用性コストをほぼ増やさない |
| **G4 接続元固定** | 許可リストに Bao ごとの接続元アドレスを登録。seal は内部ネットワークのみで待受（L2）。別の場所に持ち出された盗難 Bao は到達不能または不一致で拒否 | 外部に持ち出された盗難機（資格情報が全て有効でも） |
| **G7/N4 暗号文クラス（二重）** | 暗号文ダイジェストの**登録を seal だけでなくノードも照合**する。登録は運用者が明示ウィンドウ中に行い、**ct_registry への追加は承認付き**（§5.3） | 任意の点 `R` に対する DH オラクル化（threshold-crypto §2.7 注意 2）。**seal が侵害されても、ノードは未登録の暗号文を復号しない**ので、攻撃者の取れるものは「既に登録済みの root key blob の復号」に限定される |
| **G8 `sealed` 状態突合** | 登録アドレスの `seal-status`（無認証）で `sealed:true` を確認。起動直後の競合に備え短い再試行 | 稼働中の正規機の複製・持出機（正規機が `sealed:false` の間は拒否） |
| **G9 通知・監査** | root key クラスの decrypt は**毎回**通知。通知の無い Unwrap は存在しない設計 | 暗号的に閉じられない領域の事後検知（§4.5） |
| **N2 状態ゲート（L0）** | クラスタが `LOCKED` ならノードは部分復号を返さない | ロック後の全 Unwrap（キルスイッチ） |
| **N6 レート** | per-Bao（seal）とグローバル（ノード）の二段。root key クラスの Unwrap は**起動時のみ**で極めて稀なので、上限を低く設定できる | 総当たり・異常な連続要求・侵害された seal による濫用 |

#### 段階的な Unwrap ポリシー（運用者が選ぶ）

| ポリシー | 内容 | 使いどころ |
|---|---|---|
| **P0: 自動（既定）** | G1〜G9／N1〜N7 を通れば自動で Unwrap。通知のみ | 平常運用。Bao の自動復旧（設計概要 §2-6）を保つ |
| **P1: ゲート付き** | 上記に加えて、**事前認可チケット**（運用者 1〜2 名の assertion、有効期限 15 分程度、対象 Bao ID と `request` のダイジェストに束縛）が無い root key Unwrap を拒否 | 盗難の疑い・不審な通知が出た後、再鍵や失効が完了するまで |
| **P2: ロック** | クラスタを `LOCKED`（Tier L: 1 台で即時）。以降の全 Unwrap が不可。稼働中の Bao は継続 | 盗難発覚直後の遮断（openbao-integration §4.4.3） |

P0 → P1 → P2 の引き上げは「拒否方向」なので低い段階で即時実行でき、引き下げ（解錠）は 3-of-5（§5.3）。

#### 暗号的に閉じられない領域（明記）

> **盗難した Bao を、元のネットワーク・元のアドレス・元のブート状態のまま再接続された場合、G1〜G8 は通過する。** 資格情報（鍵・証明書・トークン・blob）がすべて正規であり、`sealed:true` も満たされ得る（ホストごと持ち去られて電源を入れ直した状態に等しい）。**認証だけでは正規の再起動と区別できない。**
> これは「認証された Bao は Unseal できる」という Auto-Unseal の性質そのものによる限界であり、閾値暗号でも閉じられない（threshold-crypto §5.1、openbao-integration §4.6）。本設計はこれを (1) G9 で**必ず通知して検知**、(2) P1/P2 で**キルスイッチとして遮断**、(3) 失効（§3.4）で**資格情報を無効化**、(4) 物理・ネットワーク境界の運用（盗難されにくい配置、アドレスの固定・監視）に依存する、の組み合わせで閉じる。

可能な強化（効果は限定的）: Bao ホストに TPM を使うローカル TLS プロキシを置き、TPM 鍵を要求する（§8.2）。盗難機が同じソフトウェア状態でブートできる場合は利用可能なままなので、**複製対策であって再接続対策ではない**。

### 4.5 盗難ノードの Unwrap 要求の拒否（まとめ）

| 攻撃者の持つ機器 | 試みる経路 | 拒否の主因（最初に効く層） | 閉じられない条件 |
|---|---|---|---|
| **Qorynth ノード 1 台** | 他ノードへ部分復号要求 | N1: `seal` ロール以外は拒否（ロール分離） | なし（Share は 1 つで `d` は得られない） |
| 同 | seal に接続 | リスナー無し／`bao` リスナーが `node` を拒否 | なし |
| 同 | 自分が seal を名乗る | 証明書は `node` ロール。`seal` リスナー・ALPN に到達不能 | なし |
| **Bao 1 台**（持出し） | seal へ Unwrap | G4（接続元不一致）・G8（元機が `sealed:false`／アドレス不一致）→ 通過しても G9 で通知 | 元のアドレスで元の状態へ戻された場合 |
| **Bao 1 台**（失効済み） | seal へ Unwrap | G3（失効）。確立済み接続は強制切断 | なし |
| **seal 1 台**（稼働機） | ノードへ部分復号 | N3（失効後）／N4（**未登録暗号文は拒否**）。登録済み root key blob の復号は可能 | 失効前に root key blob を復号された場合（検知→再鍵） |
| **Bao 1 台 ＋ Qorynth ノード 1 台**（想定脅威） | 上記の組み合わせ | Share 1 つでは `d` は得られず（オフライン）、オンラインは上記のとおり | 同上（Bao を元の場所に戻された場合） |

## 5. 承認端末の認証

### 5.1 資格情報

| 項目 | 設計 |
|---|---|
| 方式 | **WebAuthn**（W3C。署名アルゴリズムは **ES256（P-256）** を必須。他系列は不許可） |
| User Verification | **必須**（PIN・生体）。UV ビットが無い assertion は無効（threshold-crypto §5.3 の要求） |
| 資格情報の型 | **端末固定（device-bound）の資格情報を要件とする。** 登録時に authenticator data の **BE（Backup Eligible）フラグが 1 の資格情報は拒否**する。同期型パスキーは同一クラウドアカウントの漏えいで複数端末分の承認が同時に失われ、「3 台」の意味が弱まるため（承認の閾値は**端末数**を意味させたい） |
| 認証器の検証 | 登録時に attestation を取得し、**AAGUID の許可リスト**で認証器の種類を制限する【要確認: attestation の形式・検証ライブラリ】。許可リスト外の認証器は登録不可 |
| 登録の単位 | 端末ごとに 1 資格情報。**所有者ラベル**（誰の端末か）を持つ。**1 人の複数端末と別の人の端末を区別できる**ようにする |
| RP ID・Origin | 固定のドメインを RP ID とし、**assertion の `rpIdHash` と `origin` を検証**する（フィッシング対策）。RP ID のドメインを失うと全端末が再登録になるため、DNS・ドメインの保全を運用要件とする【要確認】 |
| 署名カウンタ | 逆行を**複製の疑い**として警告・隔離候補にする（同期型で常に 0 の場合は検知できないため、端末固定を要件にする根拠の一つ） |
| 承認サービスの位置づけ | `qorynth-approval` は論理サービスで、signal の承認口が仲介する。**真正性・完全性は assertion の署名で担保**し、サービス側は信頼しない |

### 5.2 3-of-5 承認の認証（承認証明書）

**承認対象のハッシュ（チャレンジ）:**

```
challenge = H( cluster_id ‖ operation ‖ parameters ‖ target_ids
             ‖ device_set_version ‖ raft_index ‖ nonce ‖ not_after )
```

| 要素 | 役割 |
|---|---|
| `operation` と `parameters`・`target_ids` | **何を承認するか**を特定（例: 有効化、ノード N の失効と Resharing、Bao B の許可リスト追加） |
| `device_set_version` | **端末集合の版**。端末の追加・失効の前に集めた承認を、後の集合に再利用させない |
| `raft_index` | 承認が束縛される状態の位置。古い状態に対する承認の再利用を防ぐ |
| `nonce` | 一意。適用関数が使用済み nonce を記録し再利用を拒否 |
| `not_after` | 有効期限（既定 10 分程度）。承認が長時間放置されても使えないようにする |

**承認証明書 `ApprovalCert`:** `{challenge の構成要素, [assertion₁, assertion₂, …]}`。各 assertion は **異なる端末の資格情報**による署名で、clientDataJSON の challenge が上記ハッシュと一致するもの。

**検証（各ノードが独立に実施。signal・approval サービスは検証しない）:**

1. 各 assertion の署名を、`devices` の公開鍵で検証（`rpIdHash`・`origin`・**UV フラグ**・署名カウンタ）。
2. **異なる有効な端末**の assertion が閾値以上あること（同じ端末の重複は 1 票）。`suspended`／失効した端末の票は数えない。
3. `device_set_version` が現行と一致、`nonce` が未使用、`not_after` が期限内。
4. 承認種別に応じた閾値（§5.3）を満たす。
5. 検証済みの証明書は Raft エントリとして**適用関数が再検証**する（§4.1）。通ったものだけが効力を持つ。

**留意すべき限界:** WebAuthn の assertion は**チャレンジに署名するだけ**で、端末の画面に何が表示されたかは暗号的に保証しない。悪意ある承認 UI が「有効化」と見せて「Bao の許可リスト追加」を承認させることが理論上できる。**承認端末のアプリ（ネイティブ／PWA）は、承認内容を自らノード側の状態から取得・再計算し、表示した内容からチャレンジを自分で組み立てる**ことを要件とし、Web ブラウザ上の単純なフォーム方式にしない【要検討: 実装形態と、承認内容の独立確認（複数ノードからの取得）】。

### 5.3 承認の段階（リボケを含む）

承認基準を操作の**方向**で非対称にする（openbao-integration §4.4.3 の「ロックは軽く、解錠は重く」の一般化）。

| 段階 | 閾値 | 操作（例） | 方向 | 根拠 |
|---|---|---|---|---|
| **Tier L（ロック）** | **1 端末**（UV 付き assertion）または復旧管理者 1 名 | クラスタを `LOCKED` に（P2）。P1 への引き上げ。緊急ローカル拒否の発行 | 拒否 | 悪用されても失うのは可用性のみ。盗難発覚から遮断までを最短に |
| **Tier S（隔離）** | **2-of-5** | ノード／seal／Bao／端末の**一時隔離**（`suspended`）。許可リストからの削除（失効）。確立済み接続の切断 | 拒否 | 盗難端末が 1 台でも他の全端末を隔離できないようにする（2 台以上は必要） |
| **Tier A（有効化・追加）** | **3-of-5** | 有効化（`LOCKED → ACTIVE`）。ノード追加・失効後の **Resharing**。許可リストへの追加（新 Bao・新 seal）。`ct_registry` への登録。証明書の発行 | 許可 | 設計概要・threshold-crypto の通常の有効化承認 |
| **Tier D（信頼の変更）** | **4-of-5 または復旧管理者鍵（M-of-N）** | **端末の追加・隔離解除（復活）**・端末集合や閾値の変更。信頼アンカー（Root/中間 CA）の更新。**Key Rotation**。復旧管理者鍵の更新 | 許可（最高） | 端末 3 台盗難で端末集合を書き換えられないようにする（threshold-crypto §5.3 の要請への回答） |

- **更新（同一 SPKI の証明書再発行）は Tier S 相当**に下げられる（権限・ロールの変更が無く、公開鍵が不変なため）。ロールや権限を変える場合は Tier A。
- **復旧管理者鍵:** 3 本の独立した署名鍵（別人・別トークン・オフライン）のうち **2 本の署名**を要する（M=2, N=3）。閾値暗号は不要で、**独立鍵の署名列を数えるだけ**にして実装を単純に保つ。genesis で公開鍵を固定する。
- **Key Rotation（threshold-crypto §4.3）を Tier D にする理由:** 新しい `d`・`key_version` の確立は信頼の最高位の操作で、攻撃者が主導すると root key の付け替え先を乗っ取れる。

### 5.4 承認端末のリボケ（失効）

| 状況 | 手順 |
|---|---|
| **端末 1 台の紛失・盗難** | 所有者が別の端末（Tier S: 2 台）で当該端末を `suspended` にする。攻撃者は 1 台では Tier S も満たせない。その後 Tier D で正式に失効し、**新端末の登録も Tier D** |
| **端末 2 台が盗難** | 攻撃者は Tier S（2-of-5）を満たせる。**残る正規端末（3 台）も隔離され得る**（可用性攻撃）。有効化（3-of-5）は攻撃者単独では成立しない。復旧は Tier D（4-of-5 は正規 3 台では足りないため**復旧管理者鍵**）で端末集合を再構成 |
| **端末 3 台が盗難**（想定の最悪） | 攻撃者は **有効化（Tier A）を単独で成立させ得る**。ただし鍵は復号できず（Share は端末が持たない。threshold-crypto §5.3）、**端末集合の変更（Tier D）は不可**。**正規の 2 台は Tier S で盗難端末を隔離でき**、レースになる。確実な回復は Tier L（ロック）→ 復旧管理者鍵による端末集合の再構成 |
| **端末の漸次的な喪失（5 台のうち 3 台が故障）** | 3-of-5 が成立しなくなる前に Tier D で補充する。**可用性の観点から、2 台までの喪失で運用が止まらないよう、端末の予備を保有**する運用とする |

- 隔離は即時に効く（Raft 適用後、以降の assertion は集合に含まれない）。復活は Tier D（誤隔離・悪意の隔離を元に戻すのは重い操作）。
- 端末集合の変更は常に `device_set_version` を進め、**進行中の承認を無効化**する。

## 6. 資格情報のライフサイクル

### 6.1 初期化（genesis 儀式）

前提: ノード・seal・signal・Bao のホストが用意され、**オフラインの管理端末**（エアギャップ）が使える。最も特権的な儀式のため、**帯域外で確認可能な入力のみ**を使う。

```
① Root CA 生成   オフライン端末で Root 鍵をトークン内に生成・自己署名。フィンガープリントを控える
② 中間 CA 生成   ロール別の中間鍵を別トークンに生成し、Root で署名（node/seal/bao/signal/admin）
③ 復旧管理者鍵   3 名がそれぞれ自分のトークンで署名鍵を生成。公開鍵だけを集める（M=2, N=3）
④ 承認端末登録   5 台の端末で WebAuthn 資格情報を登録（BE=0・UV 必須・AAGUID 検査）。公開鍵・AAGUID・所有者ラベルを集める
⑤ 主体の鍵生成   各ノード（3）・seal（2: クライアント鍵とサーバ鍵）・signal（3）の TPM 内で鍵を生成し、CSR と TPM 証明情報を提出
               Bao（3）はファイル鍵を生成し CSR を提出。運用者（admin）も CSR
⑥ 発行           中間鍵で各 CSR に署名（genesis では承認端末が未稼働のため、復旧管理者鍵 2/3 の署名で認可）
⑦ genesis 記録  以下を 1 つの記録にして署名（復旧管理者 2/3）:
                 Root/中間の公開鍵ハッシュ、各主体の SPKI ハッシュ（ノード・seal・signal・Bao と接続元アドレス）、
                 承認端末の公開鍵集合、復旧管理者の公開鍵集合、初期ポリシー
               記録のハッシュを**帯域外で確認し、各ノードに固定**
⑧ Raft 初期化   3 ノードが genesis 記録で Raft を開始。AuthRegistry を初期化
⑨ 鍵生成         threshold-crypto §4.1 の DKG（承認＝Tier D 相当: genesis 時は復旧管理者鍵＋承認端末の確認）
⑩ root key       Bao 初期化 / Seal migration の Wrap ウィンドウを運用者が開き、`ct_registry` に root key blob のダイジェストを登録
```

- ⑥ の認可は genesis 専用の例外（承認端末の稼働前）で、**以後は使えない**（genesis 記録に「例外の失効」を含める）。
- 初回の信頼を TOFU に任せない（p2p-transport §5.3）。確認できるのは、**フィンガープリント（Root・genesis ハッシュ）の帯域外確認**のみ。

### 6.2 運用中

| 事象 | 認証・資格情報の動作 |
|---|---|
| 通常の Unwrap | G1〜G9／N1〜N7（§4.4）。許可リストの鮮度を維持（スナップショット更新） |
| 証明書の更新 | 期限 30 日前に儀式（§3.3）。同一 SPKI なら許可リスト変更なし |
| Bao の入れ替え・追加 | 新 Bao の CSR → 許可リスト登録（Tier A） → 旧 Bao は Tier S で失効。接続元アドレスも更新 |
| seal の追加・交換 | seal クライアント証明書の登録（Tier A）。Bao 向けサーバ証明書の更新は Bao 側の CA ピン留めが `seal-ca` のままなら Bao 設定変更不要 |
| ノードの定期 Share Refresh | 認証に影響しない（`epoch` は暗号側。許可リストは不変） |
| 異常な通知（想定外の Unwrap） | P1 へ引き上げ（Tier L 相当） → 原因調査 → 失効・再発行 |

### 6.3 ノード失効（盗難・侵害の疑い）

threshold-crypto §4.3 の暗号側の手順に、**認証側の手順**を対応させる。

| 段階 | 認証・認可の操作 | 承認段階 |
|---|---|---|
| 1 隔離 | ノードを `INVALIDATED`、`members` から外す。**証明書チェーン・TPM ID を許可リストの拒否側へ**（失効エントリ）。他ノード・seal・signal が当該ノードの接続を即時切断 | Tier S（必要なら Tier L でロックを併用） |
| 2 新ノード登録 | 新ノードが TPM 内で鍵生成 → CSR → **Tier A** で許可リスト登録・証明書発行 | Tier A |
| 3 Resharing | threshold-crypto §4.3 の VSR。**承認証明書をエントリに添える** | Tier A |
| 4 再鍵の判断 | threshold-crypto §4.3 の Key Rotation 併用基準に従う | Tier D |
| 5 事後 | seal のスナップショットから旧ノードが消えたことを確認。盗難後に当該 ID が関与した要求が無かったか、監査ログ（G9／N7）で確認 | — |

盗難された **Bao** は §4.5・openbao-integration §4.5 の手順（許可リストから削除 → OpenBao Raft ピアから除外 → 新 ID で再発行 → 新 ID を許可リストへ登録）。

### 6.4 全台再起動

| 段階 | 認証・資格情報の動作 |
|---|---|
| 起動 | 各ノードは `LOCKED`。**TLS 鍵は TPM の永続鍵**であり、再起動後も同じ `node_id` で相互認証できる（認証は `ACTIVE` に依存しない）。Raft は永続化された AuthRegistry で再開 |
| 認証と時刻 | 証明書の有効期限判定に時刻が要る。**全台停止中に期限が切れた場合は更新儀式が先**になる。時刻同期を監視する |
| 承認 | Tier A の承認証明書（3-of-5）が `LOCKED → ACTIVE` を許可。各ノードが独立に検証してから TPM 封印鍵で Share をロード（threshold-crypto §4.5）。**承認の有効期限切れ・端末集合の版不一致なら拒否** |
| Raft の完全性 | ディスク上の Raft ログが改ざんされていないことを **genesis ハッシュからのハッシュ鎖**で確認できるようにする（複数ノードの多数派一致でも検出）【要検討: TPM NV への固定】 |
| seal の再開 | seal は **スナップショットが新鮮になった時点（ノードに到達できた時点）**で Unwrap を受け付ける（stale のままなら拒否）。起動順序は openbao-integration §5.1（Qorynth `ACTIVE` → seal → Bao）に従う |
| 1 台だけ再起動 | threshold-crypto §4.5 の推奨（クラスタ `ACTIVE`・測定起動・mTLS/TPM 認証・epoch 一致なら再承認なし）を、**許可リストに載っていて非失効**であることを必須条件に加える。盗難ノードの再接続は §4.5 で閉じる（失効済みなら拒否） |

### 6.5 実装フェーズとの対応

|---|---|
| フェーズ2 | Root/中間 CA の儀式、TPM 鍵・証明情報、AuthRegistry（`members`・`seals`・`trust_anchors`・`revocations`）、カスタム証明書検証（SAN URI・ロール照合・メンバーシップ照合）、強制切断 |

## 7. 脅威モデルとの整合

### 7.1 設計概要・threshold-crypto の想定シナリオ

| シナリオ | 認証の挙動 | 結果 |
|---|---|---|
| **Qorynth ノード 1 台＋ Bao 1 台の盗難**（想定脅威） | オフライン: Share 1 つでは `d` は得られず復号不可。オンライン: 盗難ノードは N1（ロール）で拒否、seal にもリスナー無し。盗難 Bao は G3（失効後）／G4・G8（持出し）で拒否。**元の場所・状態に戻された場合のみ通過**し、G9 で通知 → P1/P2 → 失効 | **Seal 鍵を復号できない**（要件）。オンラインの残余は検知＋遮断（§4.4 末尾） |
| **Qorynth ノード 2 台の盗難** | 閾値の定義上 `d` は復元可能（threshold-crypto §5.2）。認証は盗難ノードを遮断するが、オフラインで `d` が得られる場合は防げない | **設計上限**。Key Rotation（Tier D）＋ OpenBao rekey |
| **承認端末 3 台の盗難** | 有効化（Tier A）は成立し得るが、**端末集合の変更（Tier D）は不可**。鍵処理は不関与（Share を持たない）。正規 2 台が隔離（Tier S）・ロック（Tier L）でレース | 有効化のみ可能・復号は不可（要件を満たす）。UV 必須（§5.1） |
| **Signaling 停止** | 認可は signal に依存しない。既知の Peer 間 mTLS は継続 | 認証への影響なし（可用性のみ） |
| **Qorynth ノード 1 台の実行時侵害** | 侵害ノードは自分の Share のみ。他ノードは `seal` 以外へ部分値を返さない。**Raft の適用関数が承認を検証するため、侵害リーダーが AuthRegistry を書き換えられない**（§4.1） | 失効＋ Resharing |
| **`qorynth-seal` の侵害** | 攻撃者は seal 資格情報で部分復号を要求できるが、**ノードの N4 で未登録暗号文は拒否**。取れるのは登録済み root key blob の復号結果。失効→再発行→再鍵の判断 | 長期鍵 `d` は漏れない。root key の再鍵を判断 |

### 7.2 盗難ノードの Unwrap 拒否（threshold-crypto §5 の残課題）

§4.4・§4.5 に具体化した。要約:

1. **ロール分離**で、盗難した Qorynth ノードは seal にも他ノードの復号口にも入れない。
2. **許可リストの SPKI 固定・接続元固定・`sealed` 状態突合**で、盗難した Bao を別の場所から使えなくする。
3. **ノード側の暗号文登録照合（N4）**で、seal が侵害されても任意暗号文の復号オラクルにならない。
4. **非対称キルスイッチ（Tier L/S）と P1/P2**で、検知後の遮断時間を最短にする。
5. **暗号的に閉じられない唯一の領域**＝盗難 Bao が元の場所・状態で再接続された場合は、G9 の通知による検知と、P1/P2・失効で閉じる。この領域の存在を設計上の残余リスクとして明記する。

### 7.3 CA 秘密鍵漏洩時の対応

CA の階層ごとに、影響と対応を分ける。

| 漏洩した鍵 | 攻撃者ができること | **認可への影響** | 対応 |
|---|---|---|---|
| **`node-ca`**（中間） | `node` ロールの証明書を偽造 | **なし**（許可リストの SPKI 固定のため、登録外の鍵は拒否。`members` へ追加するには Tier A の承認が要る） | 中間を失効し新中間を儀式で作成（Tier D）。**既存の葉は SPKI が不変なので許可リスト変更不要**で、チェーンを再署名するだけ |
| **`seal-ca`**（中間） | 偽の seal サーバ証明書で **Bao ↔ seal を MITM**。特に **Encrypt（root key 平文の送信）経路で root key が漏れ得る**。Bao が pin しているのが `seal-ca` のため | **Bao 側の検証は CA ピン留めのみ**で Raft の失効が効かない（§3.4 の注記） | `seal-ca` を失効し新中間を作成（Tier D）。**Bao の設定（ピン留め CA）を更新**する必要がある。Encrypt ウィンドウ中は帯域外でサーバ証明書を確認（§4.2）。MITM の可能性がある期間に Wrap した root key は**再鍵（Seal migration）**を検討 |
| **`bao-ca`** | `bao` ロールの証明書を偽造 | なし（許可リストの SPKI 固定と接続元固定） | 同様に再発行 |
| **`signal-ca`／`admin-ca`** | signal の偽造／`admin` ロール偽造 | signal: なし（可用性のみ）。`admin`: **証明書だけでは特権操作は不可**（承認証明書が要る） | 再発行 |
| **Root CA** | 全ロールの中間を偽造 | **許可リストの SPKI 固定のため、認可は破られない**。ただし信頼アンカーの更新を試みる偽造チェーン、Bao ↔ seal の MITM は再び可能 | **新 Root を生成**し、信頼アンカーの更新を **Tier D（復旧管理者鍵 2/3）**で AuthRegistry に反映。Bao のピン留め CA も更新。**genesis の再確認** |
| **復旧管理者鍵**（2 本以上） | Tier D 相当の操作の単独実行 | **最高位の信頼の崩壊** | 3 本中 2 本以上の漏洩は、新しい復旧管理者鍵集合への移行を、**残る正規の承認端末の 4-of-5** で行う。それも不可能なら再 genesis（Key Rotation を含む全面再構築） |

**設計の要点:** 認可を **Raft の SPKI 固定の許可リスト**に置き、承認なしに登録できないため、**CA 秘密鍵の漏洩が即座に認可の突破にならない**。最も影響が大きいのは **Bao 側の `seal-ca` ピン留め**（Raft 失効が効かない唯一の経路）であり、そのためロール別中間 CA の分離（`seal-ca` を専用にする）と Encrypt ウィンドウの運用統制を置いた。

### 7.4 その他

| シナリオ | 認証の挙動 |
|---|---|
| ネットワーク分断（1 台が孤立） | 孤立ノードは Raft 多数派に入れず `ACTIVE` を維持できない。許可リストの鮮度が切れた seal は拒否 |
| Raft 多数派喪失中の失効 | Raft には書けない。**緊急ローカル拒否**（Tier L/S の署名付き deny）を到達可能なノード・seal に適用 |
| 期限切れ証明書 | 猶予なしで拒否（fail-closed）。監視で事前に更新 |
| 承認のリプレイ | `nonce`・`device_set_version`・`raft_index`・`not_after` で拒否（§5.2） |
| 悪意ある承認 UI | assertion はチャレンジにのみ署名する。承認アプリが内容を独立に再計算して表示する要件（§5.2）。完全には閉じない（§8.3） |
