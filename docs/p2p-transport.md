# P2P 通信層設計 — Qorynth

> **状態:** 設計案（フェーズ1 向け）。性能値はすべて机上見積もりであり、プロトタイプでの計測が必要。
> **関連資料:** [設計概要](design-overview.md) / [アーキテクチャ](architecture.md) / [開発計画](development-plan.md) / [閾値暗号プロトコル選定](threshold-crypto.md)

## 0. 要約

| 項目 | 方針 |
|---|---|
| データ経路プロトコル | **QUIC（RFC 9000 / 9001）+ TLS 1.3 の mTLS**。ALPN で用途を分離する |
| Signaling の役割 | **アドレス交換と接続の仲介だけ**。Signaling は鍵処理・認証の信頼点にしない |
| 冗長 Signaling | 3 台の**対等な（リーダーなし）レプリカ**。状態は自己署名レコードの LWW 収束。合意プロトコル（Raft）は使わない |
| 状態の正本 | Peer 情報はノードが保持（Signaling は再構築可能なソフトステート）。メンバーシップの正本は Raft |
| NAT 越え | 既知アドレス優先 → Signaling 仲介の UDP hole punching。外部 STUN は使わず、Signaling が観測アドレスを返す。対称 NAT は relay 任意（既定オフ）または到達可能アドレスの確保で対処 |
| MITM 対策 | 接続先 `node_id` を指定して dial し、証明書（クラスタ CA 検証 + Raft メンバーシップ照合）で相手を確定する。Signaling が返す情報は**到達先のヒントにすぎず、信頼しない** |
| 0-RTT | **使用しない**（部分復号要求のリプレイ防止。threshold-crypto.md §6.2 と一致） |

## 1. 通信レイヤーの要件

### 1.1 通信経路の分類

既存資料（architecture.md §3、threshold-crypto.md §5.4）に基づき、経路を次のとおり分類する。

| 経路 | 区分 | 内容 | 本書の対象 |
|---|---|---|---|
| `qorynth-node` ↔ `qorynth-node` | **データ経路** | Raft、DKG / Resharing の sub-share 配布（HPKE で追加暗号化） | ○ |
| `qorynth-seal` ↔ `qorynth-node` | **データ経路** | 部分復号要求・応答 | ○ |
| `qorynth-node` ↔ `qorynth-signal` | 制御経路 | Peer 登録、接続仲介 | ○ |
| `qorynth-signal` ↔ `qorynth-signal` | 制御経路 | レプリカ間同期（architecture.md で「要設計」） | ○（§3） |
| 承認端末 ↔ Signal（HTTPS/WSS） | 制御経路 | 有効化承認の伝達 | 境界のみ（§3.6） |
| `qorynth-seal` ↔ OpenBao | 別系統 | HTTP/2 + TLS 1.3 | 対象外 |

### 1.2 要件

| ID | 要件 | 根拠・補足 |
|---|---|---|
| R1 | **P2P 接続**: 固定の中央ノードなしに、NAT 配下を含む 3 ノードが相互接続できる | development-plan フェーズ1 の検証条件 |
| R2 | **信頼性**: 1 ノード停止・1 Signaling 停止・一時的なパケット損失・NAT マッピング変化に耐える。切断は短時間で検出し再接続する | design-overview §4 |
| R3 | **相互認証**: 双方向で相手を暗号的に確定する。認証根拠はクラスタ CA とメンバーシップ（TPM 保護鍵）であり、Signaling ではない | 「ノード認証: mTLS + TPM 2.0」 |
| R4 | **機密性・完全性**: TLS 1.3 以上。前方秘匿性あり。ダウングレード不可 | 「ノード通信: QUIC / TLS 1.3」 |
| R5 | **制御/データ経路の分離**: Signaling が停止・侵害されても、既存接続上の鍵処理は継続でき、Signaling は復号要求・Share・平文を見ない | architecture.md §1.4 |
| R6 | **ロール認可**: 「部分復号を要求できるのは `seal` ロールだけ」（threshold-crypto.md §5.1）を通信層の証明書ロールで強制できる | |
| R7 | **リプレイ耐性**: 部分復号要求は 0-RTT で送らない。署名つき制御メッセージには nonce と有効期限を付ける | threshold-crypto.md §6.2 |
| R8 | **失効の即時反映**: 失効ノードの新規接続拒否に加え、**確立済み接続も切断する** | design-overview「Qorynth 1台盗難」 |
| R9 | **低レイテンシ**: 確立済み接続で復号は 1 RTT。接続確立は稀 | threshold-crypto.md §6.2 |
| R10 | **運用性**: Signaling 全停止時も既知 Peer 間の通信を維持。単一 UDP ポートで運用可能 | |

**非要件:** Signaling の強い一貫性、匿名性（トポロジは Signaling に見えてよい）、大容量転送。

## 2. 通信プロトコル選定

### 2.1 比較

| 観点 | **QUIC + TLS 1.3** | WebRTC（ICE + DTLS + SCTP DataChannel） | TCP + TLS 1.3 |
|---|---|---|---|
| NAT 越え | UDP hole punching が可能。ICE 相当は自前実装（標準化は進行中のドラフト段階・要確認） | **ICE 標準搭載**（STUN/TURN）。最も枠組みが成熟 | TCP simultaneous open は NAT 実装に依存し成功率が低い。実質直接到達が必要 |
| 認証モデル | TLS 1.3 mTLS をそのまま使用。CA チェーン・SAN・ALPN を利用可 | DTLS 証明書は**SDP 内フィンガープリントで認証**するのが標準。Signaling の完全性に依存し、CA 検証型 mTLS と相性が悪い | TLS 1.3 mTLS を使用可 |
| 暗号 | TLS 1.3 必須（RFC 9001） | DTLS 1.2 が主流。DTLS 1.3 の対応は実装により差 | TLS 1.3 |
| ストリーム多重 | HOL ブロッキングなしの多重ストリーム | SCTP（DTLS 上）。実装が複雑で相互運用差がある | 単一バイト列。多重化は上位層で必要、HOL ブロッキングあり |
| 接続確立 | 1 RTT（暗号と輸送を統合）。2 RTT でアプリ応答（§7） | ICE + DTLS + SCTP で複数往復。ICE チェックを含む | TCP 1 RTT + TLS 1 RTT = 2 RTT で開始 |
| 経路変化 | **Connection Migration / パス検証**で NAT 再バインドに耐える | ICE restart が必要 | 切断・再接続 |
| 実装の重さ | 中。ライブラリは言語により成熟度が異なる（§8） | 大。カメラ・音声向けの機能が大半で不要 | 小。最も成熟 |
| UDP が遮断される環境 | 不可（フォールバック要） | TURN/TCP 等で回避可 | **可** |
| 既存設計との整合 | architecture.md / design-overview で採用済み | architecture.md に「WebRTC DataChannel 利用か」の検討記載 | — |

### 2.2 推奨と理由

**推奨: データ経路は QUIC（TLS 1.3 / mTLS）。NAT 越えの調整は QUIC 外で自前実装する（Signaling 経由の UDP hole punching）。**

1. **認証モデルが要件に合致する**: Qorynth の信頼根拠はクラスタ CA / メンバーシップと TPM 保護鍵である。WebRTC の標準的な DTLS 認証は SDP のフィンガープリントを信頼する構造で、Signaling に信頼を置く（本設計の R3・R5 と相反する）。QUIC なら TLS のクライアント証明書検証をそのまま使い、Signaling を信頼点から外せる。
2. **多重化と障害分離**: Raft・復号要求・DKG を独立ストリームまたは ALPN 別接続で流せ、Raft の遅延が復号要求を止めない。TCP では HOL ブロッキングが共有される。
3. **NAT 再バインド・IP 変更への耐性**: Connection Migration とパス検証がある。長時間接続を維持する運用と相性がよい。
4. **WebRTC を採用しない理由**: ブラウザ対応という WebRTC 最大の利点が不要（ノード間通信にブラウザは関与しない）。一方で ICE/DTLS/SCTP の依存と攻撃面が増える。ICE の NAT 越えの発想（候補収集・同時プローブ）は QUIC 上に小規模に再実装できる。
5. **TCP+TLS を主にしない理由**: NAT 越えが難しく、HOL ブロッキングがある。**ただし UDP が通らない拠点向けの代替として、到達可能なアドレスを持つ場合に限りフォールバックとして追加する余地を残す**（§8）。認証は同一の mTLS モデルを使うため、追加コストは小さい。

**QUIC 採用で受け入れるトレードオフ:**

- NAT 越えの標準手順がなく、実装・検証負荷が自前で発生する。
- 一部ネットワークで UDP が制限される。フォールバック設計が必要。
- ライブラリが言語に依存し、TPM 鍵による署名や 0-RTT 無効化などの要件を満たすか選定時の確認が必要（§8）。

### 2.3 プロトコル設定の方針

| 項目 | 方針 |
|---|---|
| TLS バージョン | TLS 1.3 のみ。TLS 1.2 以下を無効化 |
| 署名鍵 | ECDSA P-256（TPM 2.0 で標準的にサポートされる）。ノード鍵は TPM 内で非エクスポート |
| 鍵交換 | X25519 を基本とし、使用ライブラリが対応していれば X25519MLKEM768 等のハイブリッドを有効化（threshold-crypto.md §3.4 の耐量子方針と整合。対応可否は §8 で確認） |
| ALPN | `qorynth-raft/1`、`qorynth-decrypt/1`（seal ↔ node）、`qorynth-ceremony/1`（DKG・Resharing）、`qorynth-signal/1`（node ↔ signal）、`qorynth-signal-sync/1`（signal ↔ signal）。**不一致なら接続拒否**し、用途を越えた利用を防ぐ |
| 接続の単位 | Peer ペア × ALPN ごとに別接続。Raft と復号が互いの輻輳・フロー制御に影響しない（3 ノード規模なので接続数は問題にならない） |
| 0-RTT | **無効**（サーバー側でも早期データを受理しない） |
| Retry / アドレス検証 | 公開される Signaling は Retry トークンを有効化し、アドレス偽装によるリソース消費・増幅を抑える |
| キープアライブ / アイドル | 例: PING 間隔 5〜10 秒、アイドルタイムアウト 20〜30 秒。NAT の UDP マッピング保持時間（機器により 30 秒〜数分程度）より短くマッピングを維持する。値は計測で調整 |
| UDP ソケット | **1 プロセス 1 UDP ソケットを共有**（Signaling 接続・Peer 接続・hole punch が同一の外部ポートを使う）。NAT マッピングを一貫させるため必須 |

## 3. Signaling の設計（`qorynth-signal`）

### 3.1 責務と非責務

| 責務 | 非責務（やらないこと） |
|---|---|
| Peer のアドレス候補の登録・参照 | ノードの認証・認可の最終判断（データ経路の mTLS が行う） |
| 接続仲介（相手へのアドレス候補中継・同時接続開始の合図） | メンバーシップの管理（正本は Raft） |
| 観測アドレス（reflexive address）の応答 | 鍵処理・復号要求・Share の取り扱い |
| Signaling 間の状態同期 | 承認の判定（承認証明書はノードが検証する。threshold-crypto.md §4.5） |
| 承認端末向け中継口（§3.6） | 通信データの中継（relay は別機能。§4.4） |

### 3.2 信頼モデル

Signaling は**信頼できない仲介者**として設計する。侵害・不正動作時に可能なことと、その影響は次のとおり。

| 攻撃 | 可否 | 影響・緩和 |
|---|---|---|
| 登録情報・接続要求の破棄、遅延 | 可 | 可用性のみ。既知アドレス・複数 Signaling で緩和 |
| 偽アドレスの提示（攻撃者サーバーへ誘導） | 可 | 相手は mTLS を完了できず接続は失敗する（§5）。機密性は損なわれない |
| 接続要求の偽造 | 不可 | 登録レコード・接続要求はノード署名つき。対象ノードが署名とメンバーシップを検証してから hole punch を始める |
| 古い要求の再送（リプレイ） | 緩和 | nonce・有効期限・`seq`（単調増加）で拒否 |
| 第三者宛のプローブ誘導（反射） | 緩和 | 要求は署名つきメンバーからのみ受理。プローブは小パケット・レート制限・回数上限。QUIC のアンチ増幅制限（検証前は受信量の 3 倍まで）も効く |
| トポロジ（IP・稼働状況）の観測 | 可 | 許容（非要件）。Signaling との通信は TLS 1.3 で保護 |

結論: **Signaling は可用性にだけ影響し、機密性・認証には影響しない**。このため Signaling に強い一貫性や厳密な失効同期を求めない。

### 3.3 データモデル

Peer レコード（論理構造）:

| 項目 | 内容 |
|---|---|
| `node_id` | 証明書の公開鍵ハッシュ（§5.2） |
| `role` | `node` / `seal` など。証明書の値と一致すること |
| `seq` | ノードごとに単調増加する版番号。再起動で巻き戻らないよう永続化（またはブート識別子 + カウンタ）|
| `candidates[]` | アドレス候補（種別: `host` / `reflexive` / `relay`、優先度、アドレス） |
| `ttl` | 有効期間（例: 60 秒）。ハートビート（例: 15〜20 秒間隔）で更新 |
| `signature` | ノード鍵による署名（`node_id`・`seq`・`candidates`・`ttl`・発行時刻を対象） |

- **状態の正本はノード**であり、Signaling は受け取った署名つきレコードを保持する**ソフトステート**。全 Signaling が消失しても、ノードがハートビートで再登録すれば復元する。
- 接続仲介（Connect 要求）は一時データ（有効期限 30 秒程度）で永続化しない。
- 承認関連の永続状態は Signaling に置かない（承認サービス側。フェーズ3）。

### 3.4 冗長構成: 3 台対等レプリカ

**方式: リーダーなしの 3 台レプリカ + クライアント側ファンアウト + 署名つき LWW 収束。**

```
          ┌────────── signal 間メッシュ（QUIC mTLS, ALPN qorynth-signal-sync/1）──────────┐
          │                                                                                  │
      ┌───▼───┐         ┌────────┐         ┌────────┐
      │ Sig A │◄───────►│ Sig B  │◄───────►│ Sig C  │
      └───▲───┘         └───▲────┘         └───▲────┘
          │ 登録・仲介（node は全 Signaling に接続）│
   node1 ─┴────────────────┴──────────────────────┘ （node2, node3, seal も同様）
```

| 項目 | 設計 |
|---|---|
| クライアント | 各ノード / `seal` は**全 Signaling（3 台）に長期接続**し、それぞれへ登録する。最低 1 台に到達できれば動作する |
| 同期 | 受信したレコードを他の Signaling へ即時プッシュ（署名検証つき）。さらに 10〜30 秒周期で `(node_id, seq)` のダイジェストを交換するアンチエントロピーを実施 |
| 競合解決 | `node_id` ごとに `seq` が大きい方を採用（LWW）。レコードは署名つきなので Signaling による改ざん・捏造は不可。ノードは自分の `node_id` のレコードしか発行できない |
| 削除 | 登録解除・失効はトゥームストーン（`seq` つき）で伝播。TTL 切れでも自然消滅 |
| 接続仲介の転送 | 対象ノードが別の Signaling にしか接続していない場合、受け付けた Signaling が同期メッシュ経由で転送 |
| 配置 | 別障害ドメイン（別ホスト、可能なら別拠点）に置く。**公開到達可能なアドレスが必要**（rendezvous のため） |
| 発見 | ノード設定に 3 台のアドレスと CA ルートを保持（`qorynth` CLI で配布）。名前解決は複数 A / SRV を許可し、全台と接続を試みる |

**Raft を使わない理由:**

1. Raft クラスタは P2P 接続が前提であり、その接続確立に Signaling が必要なため、**起動時の循環依存**が生じる。
2. Raft は過半数（3 台中 2 台）が必要で、2 台停止で書き込み不能になる。署名つき LWW なら**1 台でも登録・参照・仲介が可能**で、可用性が高い。
3. 状態は全てノードが再生成できるため、強い一貫性による保護対象がない。

**既知の限界:**

- パーティション中は、Signaling ごとに見える Peer が異なる（古い候補が残りうる）。ノードが全 Signaling に登録するため実害は小さく、収束後に解消する。
- 失効情報は Signaling では**ベストエフォート**。失効ノードの登録を 100% 防ぐ必要はなく（データ経路の mTLS とメンバーシップ照合が防ぐ）、Signaling は証明書チェーン検証・レート制限で濫用を抑える。

### 3.5 状態保存

| 状態 | 保存先 | 失った場合 |
|---|---|---|
| Peer レコード | メモリ + 任意のローカル永続キャッシュ（再起動後のウォームスタート用） | ノードのハートビートで 1 周期以内に再構築 |
| 接続仲介の一時データ | メモリのみ | 要求側が再試行 |
| Signaling 間の同期位置 | 不要（毎回ダイジェスト比較） | 再同期 |
| Signaling 自身のサーバー証明書・秘密鍵 | ディスク（権限制限） | 再発行（クラスタ CA） |
| Signaling に置かないもの | 鍵 Share、承認の永続状態、メンバーシップの正本 | — |

ノード側（`qorynth-node`）は次をローカルに永続化する（Signaling 全停止時の復旧に必要）:

- 最後に成功した Peer のアドレス（last-known-good）
- Raft メンバーシップ内の各 Peer の最終既知アドレス
- 自身の `seq`

### 3.6 承認端末向け口の扱い（境界）

architecture.md §2.2 は承認端末が Signal 経由で承認を送るフローを描いている。承認設計はフェーズ3で扱うため、本書では次の境界だけを定める。

- 承認端末向けの口（HTTPS/WSS、WebAuthn）は、ノード向けの口（QUIC mTLS）と**別のリスナー・別の権限**とする。
- Signaling は承認の**転送のみ**行い、承認の成否を判定しない。承認証明書はノードが自分で検証する（threshold-crypto.md §4.5）。
- Signaling は承認メッセージを破棄できるが、偽造はできない（可用性のみの影響）。
- 注意: 「全 Signaling 停止 + クラスタ全台再起動」では承認の経路が失われる（§6.4、§8）。

## 4. NAT 越えと接続確立

### 4.1 方針

- **外部 STUN サービスは使わない。** 観測アドレスは Signaling が QUIC 接続で見えた送信元として応答する（外部依存・情報流出の回避）。標準化の進む QUIC のアドレス観測拡張が使えるかは §8 で確認し、使えなければ Signaling 応答に独自フィールドで載せる。
- ICE（RFC 8445）全体は実装せず、**候補の同時試行**と **QUIC ハンドシェイク自体を接続性チェックとして使う**簡易方式にする。
- **QUIC の役割を決定的に決める**: `node_id` の小さい側を QUIC クライアント、大きい側をサーバーとする（同時接続の取り合いを避ける）。

### 4.2 アドレス候補と試行順

| 順位 | 候補 | 取得元 | 備考 |
|---|---|---|---|
| 1 | last-known-good / Raft 既知アドレス | ローカル永続・Raft メンバーシップ | Signaling なしで即時試行 |
| 2 | `host`（LAN アドレス） | ローカル NIC | 同一 LAN。mDNS は開発・検証用に任意（本番で必須にしない） |
| 3 | `reflexive`（観測アドレス） | Signaling の応答 | NAT 外側アドレス。hole punch に使う |
| 4 | `relay` | relay（任意機能。§4.4） | 既定オフ |

候補は 100〜250 ms 程度ずらして**並行に**試行し、mTLS まで成功した最初の経路を採用、残りは閉じる（Happy Eyeballs 型）。IPv4/IPv6 とも対象。

### 4.3 シナリオ別フロー

**シナリオA: 同一 LAN / 直接到達可能（NAT なし、または固定アドレス・ポート開放）**

```
node A ──(既知アドレス / host 候補へ QUIC Initial)──► node B
node A ◄────────── QUIC + mTLS 完了 ───────────────► node B
Signaling 不要。
```

**シナリオB: 片側が到達可能（B が公開アドレス、A が NAT 配下）**

```
A ──► B   A から B の既知/公開アドレスへ直接 dial（NAT は A の送信で自動的に通過）
Signaling は B のアドレス更新確認にのみ使用。
```

**シナリオC: 両側が NAT 配下（エンドポイント非依存マッピングの NAT）— hole punching**

```
1. A, B: 各自、Signaling へ登録済み。観測アドレス(A*, B*)を保持。
2. A ─(Connect: to=B, candidates=A*, nonce, 署名)─► Signaling ─(転送)─► B
3. B: 署名・メンバーシップ・nonce を検証。B の候補(B*)を返す:
   B ─(Accept: candidates=B*, 署名)─► Signaling ─► A
4. 同時プローブ開始（NAT に外向きマッピングを作らせる）
   A → B*   B → A*   （小さな UDP パケットを 100〜250 ms 間隔で再送、上限 5〜10 秒）
5. 経路が開いたら QUIC ハンドシェイク（小さい node_id 側がクライアント）
   ◄── QUIC + mTLS（相手の node_id を証明書で確認）──►
6. 成功したら Signaling は不要。以後は直接接続のみ（Signaling が止まっても継続）。
```

- プローブ・Initial を同一 UDP ソケットから送るため、手順1で観測したマッピングが維持される。
- NAT の分類は RFC 4787（マッピング／フィルタリング挙動）の用語で整理。**エンドポイント非依存マッピング**の NAT なら成功しやすい。

**シナリオD: 対称 NAT（エンドポイント依存マッピング）/ CGNAT / UDP 遮断**

- hole punching は失敗しうる（宛先ごとに外部ポートが変わる）。ポート予測は成功率が不安定なため採用しない。
- 対処の優先順（推奨）:
  1. **運用で回避する**: 少なくとも 1 つのノードに到達可能なアドレス（固定 IP + ポート開放、または VPN/オーバーレイ上のアドレス）を持たせる。3 ノード構成では全ノードの間で「少なくとも片側が到達可能」であればシナリオBで足りる。
  2. **relay を有効化**（§4.4）。
  3. UDP 遮断の場合は TCP+TLS フォールバック（§8、到達可能アドレスが前提）。

**シナリオE: 接続後の経路変化（NAT 再バインド・IP 変更）**

```
- NAT 再バインド: QUIC の Connection Migration / パス検証で接続継続。
- IP 変更・長時間切断: 接続断を検出（アイドルタイムアウト）→ 再接続は §4.2 の候補順で実施。
  同時に Signaling へ新しい観測アドレスを再登録（seq 加算）。
- 両側が同時に NAT マッピングを失った場合は Signaling による再 hole punch が必要。
```

### 4.4 STUN/TURN と relay の扱い

| 選択肢 | 判断 |
|---|---|
| STUN（RFC 8489） | 外部サービスは使わない。観測アドレスは Signaling が提供 |
| TURN（RFC 8656）/ 他の中継 | **既定では採用しない**。採用する場合も Signaling とは別の役割（`qorynth-relay`）とし、データ経路に第三者が加わる点を明示する |
| relay の安全性 | 通信は端と端の mTLS で保護されるため、relay は暗号文しか見えない。影響は可用性・遅延とトラフィック解析に限る |
| relay を Signaling に統合しない理由 | 制御経路とデータ経路の分離（R5）を保ち、Signaling の帯域・障害が鍵処理に波及しないようにするため |

relay の要否は、フェーズ1 の実環境（各ノードの NAT 種別）で判断する。**判断期限は開発計画の「NAT Traversal戦略: フェーズ1内」に従う。**

## 5. データ経路のセキュリティ

### 5.1 認証モデル

接続は双方向の mTLS で、次の 3 点を**すべて**確認する。

1. **証明書チェーン**: クラスタ CA（フェーズ2 の自己署名 CA）へ検証できること。
2. **接続先の一致**: dial 時に期待する `node_id`（証明書公開鍵のハッシュ）を指定し、相手の証明書がそれと一致すること。DNS 名や Signaling が返したフィンガープリントは信頼根拠にしない。
3. **メンバーシップ照合**: ノード同士の接続では、`node_id` が現在の Raft メンバーシップに含まれ、失効していないこと。`seal` 等の非メンバーは、メンバーシップとは別の許可リスト（ロールつき）で照合する。

多層にする理由: CA の鍵が漏えいしても、メンバーシップ（Raft）に載らない証明書はデータ経路のノード接続に使えない。逆に、失効は Raft の更新で即座に反映でき、CRL の配布遅延に依存しない。

### 5.2 証明書とノード ID

| 項目 | 方針（フェーズ2 で最終確定） |
|---|---|
| ノード鍵 | TPM 2.0 内で生成した非エクスポート ECDSA P-256 鍵。TLS の署名操作は TPM 経由 |
| `node_id` | 証明書の SubjectPublicKeyInfo の SHA-256（先頭を使う場合は十分な長さを確保） |
| 証明書の識別子 | SAN の URI に `クラスタID / ロール / node_id` を載せる（例: `qorynth://<cluster>/node/<node_id>`）。DNS 名は使わない |
| ロール | `node` / `seal` / `signal` を証明書で表現（SAN URI またはロール別の発行 CA）。ノードは `qorynth-decrypt/1` で **`seal` ロールのみ**部分復号を許可（threshold-crypto.md §5.1） |
| 有効期間・更新 | 要確定。本書の要求は「失効が Raft メンバーシップで即時効くこと」「時刻依存を最小化すること」 |

### 5.3 証明書の配布とブートストラップ

| 段階 | 手順 |
|---|---|
| 初期クラスタ作成 | 管理者が `qorynth` CLI で CA ルートと 3 つのノード公開鍵を**帯域外**で確認・登録し、最初のメンバーシップを作る（初回の信頼を TOFU に任せない） |
| ノード追加 | 新ノードが TPM 内で鍵を生成し、CSR と TPM 証明情報（鍵が TPM 内にあることの証明）を提出。**3-of-5 承認**（threshold-crypto.md §4.3 の失効認可と同様）後に証明書を発行し、メンバーシップへ追加 |
| `seal` / `signal` | ロールつき証明書を同様に発行し、ノードの許可リストへ登録 |
| 設定の配布 | Signaling の 3 アドレスと CA ルートの公開情報を `qorynth` CLI で配布。Signaling から信頼情報を取得しない |

CA の保護方式（オフラインルート + 中間、閾値署名による分散など）は「固定された中央管理ノードなし」の方針との兼ね合いでフェーズ2 に委ねる（§8）。

### 5.4 MITM・なりすまし対策のまとめ

| 脅威 | 対策 |
|---|---|
| Signaling による偽アドレス誘導 | §5.1 の 3 点確認。dial 先の `node_id` を固定し、不一致なら切断 |
| 経路上の MITM（hole punch 中の割り込み） | QUIC は TLS 1.3 のハンドシェイクで相互認証。プローブ段階の UDP パケットは信頼せず、認証完了前にアプリデータを送らない |
| 失効ノード・盗難ノードの再接続 | メンバーシップから除外 + 確立済み接続の強制切断（Raft で `INVALIDATED` を適用した時点で全接続を再評価。TLS は接続時のみ検証されるため、**継続接続の再検証が必須**）|
| 盗難ノードの `seal` なりすまし | ロールは証明書で固定。ノードの鍵が TPM 内にあるため、鍵の複製は困難（ただし 1 ノード盗難の防御の本体は閾値。threshold-crypto.md §5.1） |
| リプレイ | 0-RTT 無効。署名つき制御メッセージに nonce・有効期限・`seq` |
| ダウングレード | TLS 1.3 のみ、ALPN 不一致で拒否、1.3 の署名アルゴリズムを P-256 に限定 |
| 増幅・DoS | Retry とアンチ増幅制限、接続数・要求レートの上限 |
| 時刻のずれ | 証明書の有効期限判定に時刻が必要。NTP 等で同期し、署名レコードは時刻だけでなく `seq` でも新旧判定 |
| 中継（relay）による盗聴 | 端と端の mTLS のため暗号文のみ |

## 6. 可用性・障害対応

### 6.1 障害対応表（design-overview.md §4 との対応）

| design-overview の状況 | 通信層の期待動作 |
|---|---|
| **Qorynth 1台停止** | 残り 2 台で継続。Raft は 2/3 の多数派を維持。`seal` は 3 台へ並列要求し先着 2 つを採用（ヘッジ）。停止ノードへの要求は QUIC のアイドル/ PING 失敗で検出し、以後は残り 2 台のみへ送る。復帰後は §4.2 の順で再接続 |
| **Signaling 1台停止** | 全 Signaling へ接続済みのため、残りの Signaling で登録・仲介を継続。停止した Signaling への接続は指数バックオフで再試行し、復帰後にアンチエントロピーで収束 |
| **Signaling 全台停止** | **確立済み接続はすべて継続**。既知アドレスへの再接続も可能。影響: 新規 hole punch、アドレス変更後の再発見、新ノード登録、承認端末の経路。→ 下の注意参照 |
| **Qorynth 全台再起動** | 通信層は last-known-good と Raft 既知アドレスで再接続を試みる。LOCKED への遷移と 3 台承認は通信層の責務外（threshold-crypto.md §4.5）。再接続に Signaling が必要なケースは §6.4 |
| **Qorynth 1台再起動** | 通信層は再接続と mTLS 認証、`epoch` 通知までを担当。**再有効化ルールは未確定のまま**（design-overview の「未確定」を維持。§8） |
| **Qorynth 1台盗難** | Raft でメンバーシップから除外 → 全ノードが該当 `node_id` の接続を切断・新規拒否。Signaling の登録は TTL とトゥームストーンで消える。鍵 Share 更新は閾値暗号側（threshold-crypto.md §4.3） |
| 鍵データ喪失 | 通信層は関与しない（バックアップから復旧） |
| OpenBao 関連 | 本書の対象外（`seal` ↔ OpenBao） |

> **「既知Peer間の通信は継続可能」の条件:** design-overview の記述は、(a) 既存の接続が生きている、または (b) 少なくとも片側が到達可能な既知アドレスを持つ場合に成立する。両側が NAT 配下で接続が切れ、かつ Signaling 全停止の場合は再接続できない。この限界を設計上の前提として明記する。

### 6.2 部分復号の再試行

`seal` はノード A・B・C へ並列送信し、DLEQ 検証を通った先着 2 つを採用する（threshold-crypto.md §4.2）。通信層としては次を保証する。

- 要求ごとに独立ストリーム（`request_id` つき）。1 台の遅延が他の応答を止めない。
- 全体タイムアウトを持ち、満たせない場合は上位にエラーを返す（無限待機しない）。
- 同一 `request_id` の再送に同じ応答を返しても害はないが、すべての要求をレート制限・監査ログの対象とする。

### 6.3 ネットワーク分断

| ケース | 動作 |
|---|---|
| 1 ノードが孤立 | 孤立ノードは Raft の多数派に入れず ACTIVE を維持できない。残り 2 台で継続（threshold-crypto.md §5.5） |
| 2:1 に分断 | 2 台側が継続。1 台側は復号を返さない |
| `seal` がノードに到達できない | 応答が 1 台以下なら復号不可。`seal` は 2 台構成のため、もう一方へフェイルオーバー |
| Signaling 間の分断 | 各側が独立動作。ノードが全 Signaling に登録しているため影響は小さい。復旧時に収束 |

### 6.4 複合障害の注意点

| 複合障害 | 影響 | 対処 |
|---|---|---|
| Signaling 全停止 + 全ノード再起動（両側 NAT） | 再 hole punch 不可 → 再接続できない可能性 | 最低 1 ノードに到達可能アドレスを持たせる。Signaling の別障害ドメイン配置 |
| Signaling 全停止 + 全台再起動 | 承認が Signaling 経由のままなら**有効化不能** | 承認の経路をノード直結の口でも受けられるようにする（フェーズ3で確定。§8） |
| 1 ノード停止中の Signaling 停止 | 残り 2 ノードの既存接続は継続 | 復帰ノードが再参加するには Signaling か既知アドレスが必要 |

## 7. 性能・レイテンシ

> すべて**机上見積もり**であり、フェーズ1 のプロトタイプで計測して更新する。記号: `RTT_AB` = A-B 間の往復遅延。

### 7.1 QUIC 接続確立

| 要素 | 見積もり | 備考 |
|---|---|---|
| QUIC + TLS 1.3 ハンドシェイク | 1 RTT で暗号ハンドシェイクが完了。mTLS ではクライアントの証明書を最後のフライトで送るため、**サーバーからのアプリ応答が届くまで約 2 RTT** | threshold-crypto.md §6.2 の「初回接続: 追加 1 RTT、計 2 RTT」と一致 |
| TPM 署名 | ハンドシェイクごとに双方で 1 回。TPM の ECDSA 署名はおおむね数十〜数百 ms（実機依存） | 復号の通常経路では発生しない（長期接続を再利用）。再接続時のみ |
| 0-RTT | 使用しない | リプレイ回避 |

### 7.2 分散復号の往復回数

| ケース | 往復 | 備考 |
|---|---|---|
| 確立済み接続 | **1 RTT**（`seal` → 3 台へ並列、先着 2 つで合成）+ 数 ms の計算 | LAN で約 1 ms 前後、WAN で 10〜100 ms 程度（threshold-crypto.md §6.2） |
| 初回接続 | 2 RTT（接続）+ 1 RTT（要求）+ TPM 署名 | 長期接続を維持し、実運用では稀にする |
| ノード 1 台無応答 | ヘッジ要求により追加遅延なし | キープアライブで検出を早める |

**設計要件:** ノードの ACTIVE 判定は**ローカルで適用済みの Raft 状態**を参照し、復号要求のたびに Raft の往復を発生させない。この前提が崩れると上記の 1 RTT が成り立たない。ただし失効や LOCKED 化の反映は Raft の適用遅延分だけ遅れる。

### 7.3 Signaling 経由の接続確立の遅延

`A→Signaling` を `RTT_AS`、`B→Signaling` を `RTT_BS` として、シナリオCでの目安:

```
Connect 要求の到達          ≈ (RTT_AS + RTT_BS) / 2
B の応答が A に到達         ≈ RTT_AS + RTT_BS（合計）
同時プローブ → 経路開通     ≈ RTT_AB（片道〜1 RTT）+ 再送間隔
QUIC + mTLS                ≈ 2 × RTT_AB + TPM 署名
```

例（RTT_AS = RTT_BS = 20 ms、RTT_AB = 30 ms、TPM を除く）: 仲介で約 40 ms + 経路開通で約 30〜100 ms + QUIC で約 60 ms ≒ **おおむね 150〜250 ms**。プローブ失敗・再送が多い場合は数秒〜上限（5〜10 秒）に達しうる。これは接続断後の再確立でのみ発生し、復号の通常経路には含まれない。

### 7.4 Signaling が復号経路に与える遅延

**なし。** 復号は `seal` ↔ `node` の確立済み接続上のみで行い、Signaling を経由しない。Signaling の遅延・障害は新規接続確立にだけ影響する。

### 7.5 常時負荷

| 項目 | 見積もり |
|---|---|
| Signaling へのハートビート | 3 ノード + `seal` 数台 × 全 Signaling × 15〜20 秒間隔。無視できる規模 |
| Raft | 数十〜数百バイトのメッセージを秒単位。無視できる規模 |
| キープアライブ | 接続あたり 5〜10 秒に 1 パケット |
