## 0. 要約

| 項目 | 方針 |
|---|---|
| 接続方針 | 既知アドレス優先 → Signaling 仲介の UDP hole punching（p2p-transport.md §0・§4.1） |
| 外部 STUN | 不使用。Signaling が観測アドレスを応答する |

## 1. 範囲と前提

本書は QUIC の外で行う NAT 越えの調整、Signaling 経由の UDP hole punching、候補の収集・試行順、relay の要否判断、運用上の注意点を扱う。

以下の詳細は既存設計を正とし、本書では再定義しない。

- QUIC の ALPN、0-RTT、Keep-alive、Retry: p2p-transport.md §2.3。
- mTLS の CA 検証・メンバーシップ照合: p2p-transport.md §5。資格情報・認可の具体化は seal-authentication.md に従う。
- Signaling の Peer レコード、Connect/Accept、LWW 収束: p2p-transport.md §3。

K8s Pod / VM / 物理機 / クラウドのいずれに置くかは未確定。同じ配置種別でも NAT・ファイアウォール・公開ポートの条件は異なるため、配置名だけで接続可否を判断しない。

## 2. 候補の収集

| 候補 | 取得元と用途 |
|---|---|
| last-known-good / Raft 既知アドレス | 直前に接続成功したアドレスのローカル永続記録、および Raft メンバーシップで保持するアドレス。Signaling を待たず試行 |
| host | 同一 LAN などで直接到達可能なローカル NIC のアドレス。mDNS / DNS-SD は開発・検証用に任意 |
| reflexive | Signaling が QUIC 接続の送信元として観測した外部 IP・UDP ポート。応答から取得し、外部 STUN は使わない |
| relay | 有効化した場合の `qorynth-relay` のアドレス。既定オフの間は収集・試行しない |

候補には「種別」「信頼度」「最終確認時刻」を付ける。信頼度は接続成功履歴・取得元・鮮度に基づく到達性の見込みであり、相手の認証を代替しない。期限切れや古いマッピングは成功を保証しないヒントとして扱う。

候補を登録する Peer レコードの署名・TTL・ハートビートは p2p-transport.md §3.3 に従う。Signaling から受け取った観測値はノード自身の署名済み事実とは区別し、共有レコードへ載せるときはノードがその候補を含めて署名する。署名があっても到達性や接続先 ID の保証にはしない。

IPv4/IPv6 の候補を収集する。LAN・Pod 内だけで有効なアドレス、IPv6 のスコープ、公開側からの到達性を区別し、相手から使えない候補を優先しない。

## 3. 試行順と接続確立

1. last-known-good / Raft 既知アドレスを即時試行する。
2. host → reflexive → relay の順に、候補の試行開始を 100〜250 ms ずらして重ねる（Happy Eyeballs 型）。先行候補のタイムアウトを待ってから次へ進む方式にはしない。
3. ノード間の QUIC の役割は `node_id` の小さい側がクライアント、大きい側がサーバーとする（p2p-transport.md §4.1）。双方からの UDP プローブと QUIC の役割は別に扱う。
4. 期待する `node_id` に対して mTLS まで成功した最初の経路を採用し、同じ用途の残りの接続試行を閉じる。必要な ALPN 別接続の分離は維持する。
5. 成功したアドレス・最終確認時刻を更新し、次回の既知アドレス試行に使う。

IPv4/IPv6 の両方を対象とする。候補種別の優先順を保ちつつ、片方のアドレスファミリの失敗が他方の試行を止めないようにする。

hole punch のプローブ段階の UDP は信頼しない。プローブへの応答を認証成功と見なさず、認証完了前にアプリデータを送らない（p2p-transport.md §5.4）。

Signaling 経由の確立遅延の目安は **150〜250 ms**。これは p2p-transport.md §7.3 の RTT 条件で、**TPM 署名時間を除いた机上見積もり**である。署名・候補の競合・再送により増え、失敗時は数秒〜試行上限に達しうる。性能保証値にはしない。

## 4. Signaling 経由の UDP hole punching

Connect/Accept の形式は p2p-transport.md §3 に従い、NAT 越えの調整は次の手順で行う。

1. 各ノードは共通 UDP ソケットから Signaling に接続・登録し、観測アドレスを得る。
2. ノード署名つき Connect 要求を Signaling が対象へ中継する。受信側は署名・メンバーシップに加え、nonce・有効期限・単調増加する `seq` を確認し、古い要求の再利用を拒否する（p2p-transport.md §3.2）。
3. 受信側は候補を含む署名つき Accept を返し、双方が相手の候補へ同時プローブを開始する。
4. 小さい UDP プローブを **100〜250 ms 間隔、上限 5〜10 秒**で送信する。小パケット、レート制限、回数上限を設け、第三者への反射を抑える（p2p-transport.md §4.3）。
5. 経路が開いたら §3 の役割で QUIC ハンドシェイクを進め、mTLS 完了で経路を採用する。

Signaling は信頼できない仲介者で、影響は可用性のみとする。観測値を偽装されても、証明書による相手確認・認可を省略しない。トポロジ情報の観測は既存設計で許容する。

観測アドレスは Signaling が観測して応答に載せる。QUIC のアドレス観測拡張の利用可否は未確認であり、利用できなければ応答の独自フィールドで返す（p2p-transport.md §4.1・§8.2）。IETF ドラフトへの対応を実装済みと見なさない。

同じローカルソケットを使っても、エンドポイント依存マッピングでは送信先ごとに外部ポートが変わりうる。Signaling 宛ての観測値が Peer 宛てにも使えるとは保証せず、失敗時は §5 の分岐へ進む。

## 5. シナリオ別の挙動

| シナリオ | 条件 | 挙動 |
|---|---|---|
| A | 同一 LAN / 直接到達可能 | 既知アドレスまたは host 候補で即時に接続確立を試みる。アドレスが分かれば Signaling は不要 |
| B | 片側が到達可能 | 既知アドレスを優先し、host → reflexive の順で利用可能な直接経路を探す。NAT 側から到達可能側へ送信し、必要なマッピングを作る |
| C | 両側 NAT、エンドポイント非依存マッピング | Signaling 仲介の同時 hole punching で確立を試みる。成功はフィルタリング条件にも依存 |
| D | 対称 NAT / CGNAT / UDP 遮断 | hole punching が失敗しうる。CGNAT という分類だけで失敗とは断定せず実測する。ポート予測は採用しない |
| E | 接続後の NAT 再バインド・IP 変更 | Connection Migration とパス検証を使う。双方が同時にマッピングを失った場合は再 hole punch |

シナリオ D の対処順は、p2p-transport.md §4.3 に従う。

1. **運用で回避する。最低 1 ノードに到達可能アドレスを持たせることを第一推奨**とする。固定 IP とポート公開、または VPN/オーバーレイ上の到達可能アドレスなどを配置に応じて選ぶ。
2. 必要なら relay を有効化する。
3. UDP 遮断には、到達可能アドレスを前提に TCP+TLS フォールバックを検討する。UDP relay だけで UDP 遮断を解消できるとは扱わない。

最低 1 ノードの到達性は復旧の足掛かりであり、それだけで全 Peer ペアの直接接続を保証しない。3 ノードすべての組合せで確認し、到達可能ノードを暗黙のデータ中継として扱わない。ノード間の QUIC の役割規則も変更しない。

両側 NAT で再 hole punch が必要になり、**Signaling 全停止かつ全台再起動**した場合は再接続不能となる。既知アドレスに少なくとも片側から到達できる場合は再接続を試行できる（p2p-transport.md §6.1 注記・§6.4）。通信が戻っても承認経路が Signaling のみなら有効化できない点は、同 §6.4 の別課題として残す。

配置別には次を調査し、A〜E のどれに該当するかを判定する。

| 配置 | 調査する条件 |
|---|---|
| K8s Pod | Pod / Node / Service のどのアドレスが Peer から到達可能か、CNI・SNAT・UDP 公開・NetworkPolicy、送受信で同じマッピングを保てるか。hostNetwork の採否は運用設計 |
| VM | ゲストとホストの NAT、仮想ネットワーク・ファイアウォール、公開 IP・UDP ポート公開の可否 |
| 物理機 | LAN・ルーターの NAT とフィルタリング、ポート開放・IPv6 到達性 |
| クラウド | 公開 IP、NAT Gateway 等のマッピング、セキュリティグループ・UDP 制限、オーバーレイ経由の到達性 |

## 6. relay の要否判断

relay は**既定オフ**。採用時は `qorynth-relay` として Signaling と別の役割にする（p2p-transport.md §4.4）。端と端の mTLS を終端せず、その外側で暗号化された通信を中継する。relay が見るのは暗号文と通信メタデータであり、平文の Share・鍵処理内容は見せない。可用性・遅延・帯域・トラフィック解析への影響は残る。

判断期限は開発計画の **「NAT Traversal戦略: フェーズ1内」**。フェーズ1 の実環境で各ノードの NAT 種別を調査し、シナリオ D に該当するノード・組合せがあるかを根拠に決める。

| 調査項目 | 確認内容 |
|---|---|
| 外部 IP | 各ノードから見た観測アドレス、IPv4/IPv6、公開アドレスの有無。実際の値は運用記録で管理 |
| UDP ポート公開可否 | 外部からの着信、送信、ファイアウォール設定、再起動後の到達性 |
| NAT 種別 | 非対称 / 対称 / CGNAT の分類に加え、エンドポイント非依存・依存のマッピングとフィルタリング挙動 |
| Peer ペアごとの接続 | 3 ノード全組合せの到達性、hole punch 成功率、Signaling 停止・マッピング喪失後の再接続 |

3 ノード間の**全 Peer ペア**で「少なくとも片側が到達可能」が成立する場合は relay 不要と判断する。対称 NAT かつ到達可能アドレスを持たないノードがあり、運用回避後も必要な直接接続が成立しない場合は relay を検討する。接続可能でも一部ノード停止時に必要な経路が失われないか確認する。

## 7. 実装の構成

`qorynth-transport` に quinn + rustls、verifier、hole punching をまとめる（tech-stack.md §6）。iroh は参考実装として言及するのみで依存しない。iroh の機能・維持状況は本書では裏取り済みと扱わない。

quinn の **`AsyncUdpSocket` トレイトと `Transmit`**を使い、ソケット共有を自前実装する（tech-stack.md §3.2・§7 R4）。受信は共通の入口で QUIC と hole punch のプローブを振り分け、複数タスクが同じソケットを競合して読み取らない構造にする。送信の準備待ち・受信メタデータを維持し、QUIC の動作を損なわないことをスパイクで確認する。

**1 プロセス 1 UDP ソケット**を共有し、Signaling 接続・Peer 接続・hole punch に同じローカルポートを使う。NAT 外部でも同じポートを使う設計意図は p2p-transport.md §2.3 に従うが、実際の外部マッピングの同一性は §4 のとおり NAT 挙動に依存する。IPv4/IPv6 を単一ソケットで扱えることも対象環境で検証する。

フェーズ1 冒頭で同一ソケットによる登録・観測・同時プローブ・mTLS 成立までを検証する。不足する場合は **quiche（Sans-IO）または s2n-quic**への切替を比較する（tech-stack.md §7 R4）。切替時も候補順・認証・ソケット共有の要求を維持する。

2026-11-17 に crates.io の公開メタデータで quinn・rustls・quiche・s2n-quic の更新継続と非 yanked の安定リリースを確認した。これは本設計への統合成功や監査済みであることを意味しない。公開 API は docs.rs で確認し、組合せ・ソケット共有は実装検証に残す。

- 維持状況: [quinn](https://crates.io/crates/quinn)、[rustls](https://crates.io/crates/rustls)、[quiche](https://crates.io/crates/quiche)、[s2n-quic](https://crates.io/crates/s2n-quic)。
- API: [AsyncUdpSocket と Transmit を使う送信口](https://docs.rs/quinn/latest/quinn/trait.AsyncUdpSocket.html)。

## 8. 運用上の注意点

- Signaling は**公開到達可能な別障害ドメインに 3 台**置く（p2p-transport.md §3.4）。K8s / VM 等の具体的配置は未確定。
- Signaling 全停止時も確立済み接続は継続する。既知アドレスへの直接再接続は可能だが、新規 hole punch は不可。アドレス更新後の再発見にも影響する。
- Signaling のデプロイ方式、公開 IP、DDoS 対策は運用設計で決める（p2p-transport.md §8.2）。
- TCP+TLS フォールバックの採否は実環境の要望次第であり、到達可能アドレスが前提（p2p-transport.md §8.4）。
- フェーズ1 のプロトタイプで hole punch 成功率・確立時間・再接続時間を計測する。配置・Peer ペア・IPv4/IPv6・NAT 条件・TPM 署名時間を分けて評価する。
- 計測後に p2p-transport.md §7 を更新することを後続作業とする。今回の作業では既存設計書を編集しない。
