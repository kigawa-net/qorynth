# 閾値暗号プロトコル選定 — Qorynth

> **状態:** 設計案（プロトコル選定）
> **対象:** `qorynth-node`（3台）の 2-of-3 分散復号と、鍵Share のライフサイクル
> **関連:** [設計概要](design-overview.md) / [アーキテクチャ](architecture.md) / [開発計画](development-plan.md)（フェーズ5・7）

本書は、設計概要・アーキテクチャで「未確定」とされている **閾値暗号方式** を選定し、鍵ライフサイクルと脅威モデルへの適合を示す。実装コードは含まない。秘密値・認証情報も含まない（記号表記のみ）。

## 0. 要約

| 項目 | 結論 |
|---|---|
| Auto-Unseal 用の方式 | **Feldman VSS 付き (2,3) Shamir 共有 + 閾値 HPKE 復号**（P-256）。秘密鍵 `d` を再構成せずに、各ノードの部分復号を合成する「真の分散復号」 |
| 鍵生成 | 分散鍵生成（**GJKR99 の New-DKG**）。単一ノードも `d` を知らない。MVP のみ、オフライン Dealer での初期化を暫定許容 |
| Share更新・ノード失効 | Share Refresh（ゼロ多項式の加算）と **Verifiable Secret Redistribution（VSR）による再シェアリング**。公開鍵 `Y` は不変なので既存の暗号文は再暗号化不要 |
| 将来の署名 | 暗号用とは**別の鍵**として FROST（RFC 9591, P-256 / Ed25519）を第一候補とする。ECDSA 互換が必要なら DKLs23 / CGGMP21。GG18/GG20 は採用しない |
| 主な残余リスク | (1) 2ノード同時盗難は設計上限、(2) 楕円曲線ベースのため量子計算機に対し長期機密性が弱い（算法アジリティで緩和）、(3) 稼働中ノードの実行時侵害 |
| MVP フォールバック | OpenBao 標準 Shamir（n=3, t=2）の Unseal Key Part をそのまま各ノードに預ける方式。新規暗号実装なしで検証可能だが「分散復号」ではない（§2.6） |

**用語上の注意（既存資料との整合）**
既存資料の「Unseal Key Part」は、OpenBao 標準 Shamir Seal の鍵片と、Auto-Unseal で Seal が保護する root key（barrier key）の両方の意味で読める。Qorynth から見れば、どちらも **不透明なバイト列のラップ／アンラップ対象**である。本書は後者（KMS 型の Wrap/Unwrap）を主設計とし、前者は MVP フォールバックとして扱う。OpenBao が提供する Seal 種別（Transit 型や PKCS#11 型など）との接続方式は §6 の未解決事項とする。

## 1. 要件定義

### 1.1 「2-of-3 分散復号」の意味

- 秘密 `d` を 3 ノードに (t=2, n=3) で分散保持する。
- **任意の 2 ノード**が協力すれば復号できる。**1 ノード単独では復号できない**（1 Share は `d` について情報を与えない）。
- 復号の過程で **`d` がどのノードにも再構成されない**ことを強く要求する（§2.7 で再合成方式との違いを説明）。1 ノードの実行時侵害でも `d` が漏れない、という「1 ノードでは不可」の実質的な意味はここで初めて満たされる。
- 部分復号の不正（誤った値の返却）を**検出できる**こと。2 台のうち 1 台が壊れた値を返しても、誰が不正かを特定できる。

### 1.2 Share の更新と失効時の再シェアリング

用語を以下のように区別する。混同すると防御範囲を誤るため重要。

| 操作 | 委員会（保持ノード集合） | 秘密 `d` | 公開鍵 `Y` | 目的 |
|---|---|---|---|---|
| **Share Refresh**（定期更新） | 同じ | 不変 | 不変 | 異なる時期に漏れた Share を組み合わせられなくする（mobile adversary 対策） |
| **Resharing**（再シェアリング） | **変更あり**（失効ノードを新ノードに入替） | 不変 | 不変 | ノード失効・交換。旧Share と新Share は混ぜても `d` を復元できない |
| **Key Rotation**（鍵ローテーション） | 同じ／変更 | **新規生成** | **変更** | `d` 自体が漏れた疑いがある場合。暗号文の rewrap が必要 |

重要な性質: Refresh と Resharing は `d` を変えないため、**旧世代の Share が閾値（2つ）以上漏れていれば `d` は漏れたまま**である。盗難ノード 1 台（旧Share 1 つ）の失効では Resharing で足りるが、旧世代の Share を別経路（バックアップ等）から追加で入手され得る場合は Key Rotation を併用する（§4.3）。

### 1.3 鍵の種類

対称鍵と非対称鍵は、**必要な性質が異なるため別の鍵・別のプロトコルとして扱う**。同一の秘密を暗号用と署名用に兼用しない（鍵分離）。

| 観点 | 対称鍵（Auto-Unseal 用） | 非対称鍵（将来の署名用） |
|---|---|---|
| 用途 | root key / Unseal Key Part のラップ・アンラップ | JWT / X.509 / コード署名など |
| 要求される操作 | 暗号化は誰でも（または公開操作）、復号のみ 2-of-3 | 署名のみ 2-of-3、検証は公開鍵で誰でも |
| 長期秘密の形 | 下記のとおり EC スカラー `d`（HPKE の受信者鍵） | 署名鍵スカラー `x`（別DKGで生成） |
| 推奨プロトコル | 閾値 HPKE 復号 | FROST / 閾値 ECDSA |

**「対称鍵なのに EC スカラーを共有するのか」について。** Auto-Unseal で保護したいデータの暗号化方式は AES-256-GCM（対称）で変わらない。ただし AES は閾値化に不向きである（MPC による分散 AES は重い）。そこで、長期秘密は楕円曲線の受信者鍵 `d` とし、暗号文ごとに HPKE の KEM で一回限りの AES-256 鍵を導出する（ハイブリッド暗号）。データ保護は AES-256-GCM、鍵の分散は楕円曲線上の Shamir という分担になる。

### 1.4 鍵サイズと強度

| 要素 | 第一候補 | 代替 | 備考 |
|---|---|---|---|
| データ暗号（DEM） | AES-256-GCM | — | 暗号文ごとに HPKE が新規鍵・新規nonceを導出するため nonce 再利用の懸念がない |
| KEM / 長期鍵 | **P-256**（約128bit強度） | P-384（約192bit） | TPM 2.0・WebAuthn・FIPS と相性が良く、FROST(P-256) の暗号スイートも RFC 9591 に存在する |
| KDF / ハッシュ | HKDF-SHA256 | HKDF-SHA384（P-384時） | HPKE の暗号スイートに従う |
| 将来の署名 | Ed25519 / ECDSA P-256 | P-384 | 用途（検証側の互換性）で決める（§3.2） |

HPKE（RFC 9180）の Base モードで `DHKEM(P-256, HKDF-SHA256)` + `HKDF-SHA256` + `AES-256-GCM` を想定する。標準形式の暗号文にすることで、クライアント側（暗号化側）は既存の HPKE 実装を使え、Qorynth 固有なのは「復号側」だけになる。

> **強度の注意:** DEM が AES-256 でも、鍵をラップする KEM は P-256（約128bit、かつ量子計算機に弱い）で律速される。この点は §3.4 と §6 で扱う。

### 1.5 可用性要件

| 状況 | 要件 | 本設計での実現 |
|---|---|---|
| Qorynth 1台停止 | 鍵処理を継続 | 任意の 2 台で復号可能（Share を再配布する必要なし） |
| Qorynth 2台停止 | 鍵処理は不可（許容） | 閾値未満。OpenBao が稼働中でも再起動時に Unseal できない |
| 全台再起動 | `LOCKED` に戻り、再承認が必要 | Share は暗号化保存のみ。承認後に各ノードがメモリへ復号ロード（§4.5） |
| 停止ノードの復帰 | Share 世代の不整合を検出し、必要なら再同期 | 世代（epoch）とコミットメントのハッシュを Raft 状態と照合（§4.5） |
| Signaling 停止 | 既知 Peer 間の復号は継続 | 復号はデータ経路のみ使用（§5） |

## 2. プロトコル候補の比較

> **表記の補足（依頼文の語句について）**
> - 「GGS84」に対応する既知の DKG プロトコルを特定できなかった。DKG の標準的な引用先として **Pedersen（1991）** と **Gennaro–Jarecki–Krawczyk–Rabin（GJKR, 1999）** を採用する。
> - 「Frobenius」は閾値 ECDSA の方式名として存在しない。閾値署名の代表例として **GG18 / GG20、CGGMP21、DKLs23**（閾値 ECDSA）と **FROST**（閾値 Schnorr）を扱う。
> - **MuSig2 は n-of-n のマルチ署名**であり、(2,3) のような閾値署名ではない。閾値用途には FROST を使う。

### 2.1 Shamir's Secret Sharing（SSS）基本形

| 項目 | 内容 |
|---|---|
| 概要 | 秘密 `s` を定数項とする次数 t−1 の多項式 `f` を作り、Share `f(i)` を配る。t 個の Share から Lagrange 補間で `s = f(0)` を復元する（Shamir 1979）。(2,3) なら 1次式（直線） |
| 2-of-3 分散復号 | **不可（再構成が必須）**。復号には t 個の Share を一箇所に集めて `s` を復元する必要がある。秘密分割であって分散復号ではない |
| 鍵更新 | 単体では不可（Dealer が必要） |
| 実装難度 | 低 |
| 既知の弱点 | Share の正しさを検証できない（Dealer・参加者の不正に弱い）。再構成点が単一障害点（そのノードが `s` 全体を握る）。1 つの Share は情報理論的に安全 |

### 2.2 (t,n)-SSS の再シェアリング（Share Refresh / Redistribution）

| 項目 | 内容 |
|---|---|
| 概要（Refresh） | 各ノード `i` が定数項 0 のランダム多項式 `g_i` を作り、`g_i(j)` をノード `j` に送る。新 Share は `s_j' = s_j + Σ_i g_i(j)`。`s` は変わらず Share だけが入れ替わる（Herzberg ら 1995, Proactive SS） |
| 概要（Redistribution） | t 個の旧保持者が自分の Share を新しい多項式で再度 (t,n') 分割し、新委員会に配る。新 Share `s'_j = Σ_{i∈S} λ_i · h_i(j)`（λ は集合 S の Lagrange 係数）。**秘密を再構成せずに**委員会を入れ替えられる（Desmedt–Jajodia 1997, Wong–Wang–Wing 2002 の VSR） |
| 2-of-3 分散復号 | 単体では不可（復号は 2.1 と同じ） |
| 鍵更新 | **可**。公開情報（暗号文・公開鍵）は変わらない |
| 実装難度 | 中。参加者間の同期・失敗時ロールバックが必要 |
| 既知の弱点 | 検証手段を足さないと、不正な sub-share を注入されても検出できない。旧世代の Share が閾値以上すでに漏れていれば救えない（`s` が不変のため）。旧Share の消去とバックアップ失効が運用上必須 |

### 2.3 検証可能 SSS（Feldman VSS / Pedersen VSS）

| 項目 | Feldman VSS（1987） | Pedersen VSS（1991） |
|---|---|---|
| 概要 | 係数に対する公開コミットメント `C_k = a_k·G` を公開。受信者は `s_j·G = Σ_k j^k · C_k` で Share を検証 | 二つ目の生成元 `H` を使い `C_k = a_k·G + b_k·H`（Share は `(f(j), f'(j))` の組） |
| 秘匿性 | 計算量的（`C_0 = s·G` が公開される） | **情報理論的**（コミットメントから `s` が一切漏れない） |
| 束縛性 | 情報理論的 | 計算量的（`log_G H` が不明であること） |
| 2-of-3 分散復号 | **可**（EC 上の暗号と組み合わせたとき。§2.4・§2.7） | 同左（ただし公開鍵 `s·G` を別途導出する必要） |
| 鍵更新 | 可（コミットメントを更新して検証付き Refresh / Redistribution が可能） | 可 |
| 実装難度 | 中（楕円曲線のスカラー演算と多項式評価のみ） | 中〜高（`H` の生成に「誰も離散対数を知らない」性質が必要） |
| 既知の弱点 | 公開鍵 `s·G` が漏れる性質は、ECベースの暗号では元々公開されるため問題にならない。ただし長期の量子耐性を求める**対称鍵そのもの**の共有には向かない | 公開鍵の導出に追加の段階が必要 |

本設計では公開鍵 `Y = d·G` を暗号化側に配る必要があるため、**Feldman 型のコミットメントが自然**である。

### 2.4 分散鍵生成（DKG）— Pedersen DKG / GJKR99

| 項目 | 内容 |
|---|---|
| 概要 | Dealer なしで、各ノードが自分の多項式を VSS で配り、受け取った Share を足し合わせる。`d = Σ_i a_{i0}`、Share `s_j = Σ_i f_i(j)`。誰も `d` を知らない |
| Joint-Feldman（Pedersen の DKG） | 構成が単純だが、**公開鍵の分布を敵が偏らせられる**ことが GJKR により示された（rushing adversary）。署名用途では実害が小さいとの分析もあるが、一般には証明が弱い |
| **GJKR99 New-DKG** | 第1段階で Pedersen VSS（情報理論的に秘匿）で配り、第2段階で Feldman コミットメントを公開して `Y` を抽出する。**一様分布を保証**。n ≥ 2t'+1（t'=不正許容数）が必要で、n=3 では不正 1 まで許容できる |
| 2-of-3 分散復号 | **可**（DKG の出力は Feldman 形式の (2,3) Share と公開鍵 `Y`、各 Share の公開値 `Y_i = s_i·G`） |
| 鍵更新 | 可（同じ VSR / Refresh を適用できる） |
| 実装難度 | 中〜高。ラウンド同期・苦情処理（complaint）・失格（disqualification）の状態遷移を実装する必要がある |
| 既知の弱点 | 同期的な全員参加が前提（3 台全員がオンライン）。不正ノードの扱いは「失格 → 残りで再構成」で処理する。ブロードキャストチャネルが必要（Raft ログで代替できる、§4.1） |

### 2.5 閾値署名（将来の署名用）

| 方式 | 概要 | (2,3) 可否 | 実装難度 | 既知の弱点・注意 |
|---|---|---|---|---|
| **FROST**（Komlo–Goldberg 2020, RFC 9591） | 閾値 Schnorr 署名。2 ラウンド（事前コミットで 1 ラウンドも可）。暗号スイートに P-256 / Ed25519 / ristretto255 / secp256k1 などを含む | 可 | 中 | Ed25519 / Schnorr 検証にしか使えず、**ECDSA 検証側には使えない**。署名セッション中の並行実行の扱いに注意 |
| **DKLs23**（Doerner ら 2023） | 閾値 ECDSA。3 ラウンド。Paillier 不使用、OT ベース | 可 | 高 | 比較的新しく実装・監査の蓄積が浅い |
| **CGGMP21**（Canetti ら 2021） | 閾値 ECDSA。UC 安全性・Identifiable Abort・Proactive 対応 | 可 | 高 | Paillier・ZK 証明が重く実装が難しい |
| **GG18 / GG20** | 閾値 ECDSA の初期の実用方式 | 可 | 高 | 実装上の攻撃（Alpha-Rays、TSSHOCK など）が報告されている。**新規採用しない** |
| **MuSig2**（BIP-327） | Schnorr マルチ署名（**n-of-n**） | **不可** | 中 | 閾値方式ではない |

いずれも**暗号用の鍵とは別に、別の DKG で生成した鍵**で運用する。

### 2.6 OpenBao 標準 Unseal Key の分割（Shamir, n=3, t=2）

| 項目 | 内容 |
|---|---|
| 概要 | OpenBao の標準 Shamir Seal を `secret_shares=3, secret_threshold=2` で初期化し、3 つの Unseal Key Part を各 Qorynth ノードに保管する。起動時に 2 つの Part を `qorynth-seal` が集め、OpenBao の unseal API へ投入する。OpenBao 側の Shamir 実装は GF(2^8) 上でバイト単位に分割する |
| 2-of-3 分散復号 | **不可**。Part は OpenBao 側で再構成される。Qorynth は鍵片の保管庫であり、復号を行わない |
| 鍵更新 | OpenBao の `rekey`（運用者による操作）が必要で、Qorynth 単独で Share 更新・ノード失効ができない |
| 実装難度 | **最も低い**（新規暗号実装がほぼ不要） |
| 既知の弱点 | 平文の鍵片がネットワーク上と `qorynth-seal` のメモリに現れる。失効のたびに OpenBao の rekey が必要。汎用鍵管理（署名・復号）へ拡張できない。検証・不正検出がない |

評価: **MVP の足場としては有用**だが、本書の要件（分散復号・Qorynth 側での Share 更新・汎用基盤）を満たさない。最終形としては採用しない。

### 2.7 分散復号 vs 単純な秘密分割＋再合成

この区別が本設計の中心である。

| 観点 | 秘密分割＋再合成（SSS 基本形・§2.6） | 分散復号（閾値暗号） |
|---|---|---|
| 復号の流れ | 2 ノードが Share を 1 箇所へ送り、**そこで `d` を復元**してから復号 | 各ノードが**自分の Share で部分復号**を計算し、結果だけを合成する |
| `d` が存在する場所 | 復元を行ったノードのメモリ上に一時的に全体が現れる | **どこにも現れない**（鍵生成時も、DKG なら同様） |
| 1 ノードの実行時侵害 | 侵害ノードが再構成役になる、または再構成役の窃取で `d` 全体が漏れる | 侵害ノードが得るのは自分の Share と、自分が計算した部分値のみ |
| 漏れた場合の被害範囲 | 長期鍵 `d` 全体（過去・将来の全暗号文） | 合成役は**その暗号文の一回限りの KEM 共有値**のみ（長期鍵は漏れない） |
| 実装コスト | 低 | 中（部分復号の正当性証明・合成・Lagrange 係数） |

閾値 HPKE 復号の中身（記法: 群の位数 `q`、生成元 `G`、`d`、`Y = d·G`、`f(x) = d + a·x mod q`、Share `s_i = f(i)`、`Y_i = s_i·G`）:

```
暗号化（公開操作・クォーラム不要）:
  標準 HPKE Base モードで Y 宛に暗号化 → 暗号文 (R = r·G, ct)

復号（分散）:
  合成役（qorynth-seal）が R と文脈情報を ノード i, j に送る
  ノード i:  D_i = s_i · R       ＋ 正当性証明 π_i（Chaum–Pedersen DLEQ:
                                   log_G(Y_i) = log_R(D_i) を証明）
  合成役:    π_i, π_j を検証（Y_i は公開コミットメントから導出）
             S = λ_i · D_i + λ_j · D_j  （= d · R、HPKE の DH 出力）
             HPKE の鍵導出 → AES-256-GCM で復号

  Lagrange 係数（集合 {i, j}, mod q）:  λ_i = j / (j − i),  λ_j = i / (i − j)
  検算例 {1,2}: f(0) = 2·f(1) − f(2) = 2(d + a) − (d + 2a) = d ✓
```

**注意点:**
1. 合成役は暗号文ごとの `S = d·R` を知る。Auto-Unseal では復号結果（root key）自体が合成役を通るため、これは受容する。重要なのは長期鍵 `d` が合成役にも渡らないこと。
2. ノードは任意の点 `R` に対する `s_i·R` を返す「DH オラクル」になり得る。したがって**主防御は認可**である（`qorynth-seal` の mTLS ロール検証・`ACTIVE` 状態・レート制限・監査）。将来、半信頼クライアントへ汎用復号 API を公開する場合は、CCA 安全性を証明済みの閾値方式（Shoup–Gennaro TDH2 など）を検討する。
3. ノードは `R` が曲線上の有効な点であり無限遠点でないことを検証する（P-256 は余因子 1 のため小部分群攻撃の懸念は小さい）。

### 2.8 補足候補: 複製秘密分割（RSS）＋分散 PRF

量子耐性が必要な対称鍵向けに、`k = k1 ⊕ k2 ⊕ k3` とし、ノード A に {k1,k2}、B に {k2,k3}、C に {k1,k3} を持たせる方式がある。任意の 2 ノードで 3 成分すべてが揃い、1 ノードでは 1 成分が欠ける。暗号文ごとの鍵は `KEK_ctx = HMAC(k1,ctx) ⊕ HMAC(k2,ctx) ⊕ HMAC(k3,ctx)` とし、各ノードは自分が持つ成分の HMAC だけを返す。

| 項目 | 内容 |
|---|---|
| 分散復号 | 可（`k` を再構成せず、HMAC のみ使用） |
| 利点 | 実装が単純。AES / HMAC のみで量子耐性がある |
| 弱点 | **部分値の正当性を検証できない**（誤りは AEAD タグ失敗でしか分からず、不正ノードの特定が難しい）。**ノード失効時の再シェアリングが標準化されておらず**、設計と証明を自前で行う必要がある。署名への拡張経路がない |
| 位置づけ | 量子耐性が必須になった場合の併用・代替候補（§3.4）。現時点では採用しない |

### 2.9 比較サマリ

| 方式 | 分散復号 | 検証可能 | 失効時の再シェア | 署名への拡張 | 実装難度 | 量子耐性（長期機密） |
|---|---|---|---|---|---|---|
| SSS 基本形 | ✕（再合成） | ✕ | △（要 Dealer） | ✕ | 低 | ◎（情報理論的） |
| SSS 再シェアリング単体 | ✕ | ✕ | ◎ | ✕ | 中 | ◎ |
| Feldman/Pedersen VSS + 閾値 HPKE | **◎** | **◎** | **◎（VSR）** | ○（同じ共有基盤） | 中 | ✕（楕円曲線） |
| DKG（GJKR99） | ◎（鍵生成側） | ◎ | ◎ | ○ | 中〜高 | ✕（楕円曲線） |
| 閾値 ECDSA / FROST | 署名のみ | ◎ | ○ | ◎ | 高 | ✕ |
| OpenBao 標準 Shamir | ✕ | ✕ | △（OpenBao rekey） | ✕ | 最低 | ◎ |
| RSS＋分散 PRF | ○ | ✕ | △（未標準） | ✕ | 低〜中 | ◎ |

## 3. 選定と設計判断

### 3.1 Auto-Unseal 用途での推奨方式

> **採用: Feldman VSS 付き (2,3) Shamir 共有 + 閾値 HPKE 復号（P-256 / HKDF-SHA256 / AES-256-GCM）。**
> 鍵生成は GJKR99 New-DKG、Share 更新とノード失効は VSR による Resharing。

選定理由:

1. **要件 1.1 の実質を満たす唯一の現実的な方式**。再合成方式では「1 ノードでは不可」が、再構成役ノードの実行時侵害で崩れる。閾値 HPKE 復号なら 1 ノードの侵害で `d` は得られない。
2. **簡素性**。必要な暗号プリミティブは、P-256 のスカラー演算・多項式評価・Lagrange 補間・DLEQ 証明・HPKE の 5 つで、MPC や Paillier のような重い要素がない。部分復号は 1 回のスカラー倍算で済み、性能面の懸念もない（§6）。
3. **公開鍵・暗号文が不変**。Refresh / Resharing で `Y` が変わらないため、OpenBao に保存済みのラップ済み root key を再暗号化せずに運用でき、ノード失効が暗号文の再書き込みを伴わない。
4. **標準形式**。暗号化側は標準 HPKE（RFC 9180）で実装でき、Qorynth 固有の領域が復号側に限定される。
5. **署名への道筋が連続している**（§3.2）。同じ Feldman / VSR / DKG の基盤を FROST に流用できる。

### 3.2 将来の拡張（署名・非対称）への道筋

| 段階 | 内容 |
|---|---|
| ステップ 1（Auto-Unseal） | 本書の方式。鍵 ID と用途（purpose）をメタデータとして鍵ごとに管理する。暗号文ヘッダに `suite`（アルゴリズム識別子）と `key_id`・`key_version` を持たせ、算法アジリティを確保する |
| ステップ 2（汎用暗号化・復号） | 同方式で別の `key_id` を追加する。外部クライアントへ復号 API を出す場合は、部分復号の正当性証明に加えて暗号文検証付き（TDH2 系）への移行を検討する |
| ステップ 3（署名） | **暗号用とは別の DKG**で署名鍵を生成する。Schnorr / Ed25519 で足りるなら **FROST**（RFC 9591）。X.509・JWT(ES256)・WebAuthn など ECDSA 検証が必須なら **DKLs23 または CGGMP21** を評価する |
| ステップ 4（量子耐性） | §3.4 を参照 |

鍵分離の原則: 用途ごとに独立した `d` を持ち、署名鍵と復号鍵に同じ Share を使い回さない（相互の脆弱性が波及するため）。

### 3.3 採用しない方式と理由

| 方式 | 採用しない理由 |
|---|---|
| SSS 基本形のみ（再合成型） | 再構成役の実行時侵害で `d` 全体が漏れ、「1 ノードでは不可」を満たせない |
| OpenBao 標準 Shamir を最終形とする案 | 平文の鍵片がネットワークと `qorynth-seal` に現れる。失効のたびに OpenBao rekey が必要で、署名・暗号化など汎用基盤へ進めない。**MVP のみ許容** |
| Pedersen の Joint-Feldman DKG（素の形） | 公開鍵分布の偏りを敵が作れることが知られており、証明が弱い。n=3 の稀な儀式なので New-DKG の追加ラウンドを許容できる |
| GG18 / GG20 | 実装攻撃が報告されており、新規採用の理由がない（署名が必要になった時点で DKLs23 / CGGMP21 を評価） |
| MuSig2 | n-of-n であり、2-of-3 を表現できない |
| 閾値 BLS | ペアリング曲線が必要で、HPKE 標準・TPM・FIPS との相性が悪い。暗号用途には使えず、署名専用。要件に対して過剰 |
| MPC による分散 AES | 計算・通信コストが大きく、運用が複雑。ハイブリッド暗号で十分 |
| RSS＋分散 PRF（単独） | 検証不能で、失効時の再シェアリングを自前で設計・証明する必要がある（§2.8）。量子耐性が必須化したときに併用を検討 |
| TEE（SGX/SEV 等）に鍵を載せる案 | 本書のスコープ外（ハードウェア依存の信頼を追加する方向）。HSM / TPM の選択（設計概要 §6）と合わせて別途検討する |

### 3.4 量子計算機に関する扱い

- 本方式の KEM は楕円曲線（P-256）であり、**将来の大規模量子計算機（Shor）に対して長期機密性が弱い**。盗難された OpenBao のディスクにはラップ済み root key が保存されているため、「今盗んで将来解く」リスクが理論上存在する。
- 緩和策（優先順）:
  1. 暗号文ヘッダの `suite` による算法アジリティ。耐量子 KEM の閾値方式が成熟した時点で移行する。
  2. 長期機密性が必要になった場合に限り、ハイブリッド化（楕円曲線 KEM の出力と §2.8 の RSS-PRF 出力を HKDF で結合）を採用する。
  3. 受容するリスクとして明記する（現時点の脅威モデルは物理盗難・実行時侵害で、量子は想定外）。

### 3.5 トレードオフ

| 軸 | 判断 |
|---|---|
| 実装難度 vs 安全性 | SSS 再合成（最も易）より中程度の難度を許容し、「`d` を再構成しない」性質を取る。MPC や閾値 ECDSA のような高難度は将来用途に限定する |
| 安全性 vs 運用性 | 失効時は Resharing を標準手順とし、侵害度が高い場合のみ Key Rotation を追加（運用手順で段階化）。旧世代バックアップの失効が運用負荷になる |
| 簡素性 vs 量子耐性 | 簡素性を優先し、量子耐性は算法アジリティで将来に委ねる |
| 検証可能性 vs 実装量 | Feldman コミットメントと DLEQ 証明で不正ノード特定を可能にする代わりに、コミットメントの管理（Raft ログへの格納）が増える |
| MVP 速度 vs 最終形 | MVP は標準 Shamir 預託で早期に E2E 検証し、フェーズ5で閾値 HPKE に置換する（§6.1） |

## 4. 鍵ライフサイクル設計

### 4.0 保持データと世代

| データ | 保管場所 | 機密性 |
|---|---|---|
| Share `s_i` | 各ノードのローカル（暗号化保存）。稼働中は保護メモリ（`mlock`・コアダンプ無効・使用後ゼロ化） | **秘密** |
| 公開鍵 `Y`、コミットメント `C_k`、各 Share の公開値 `Y_i`、`key_id`・`epoch` | Raft ログ（クラスタ状態） | 公開（改ざん防止のみ必要） |
| ノード暗号化鍵（Share 保存用・TPM封印） | 各ノードの TPM | 秘密 |
| 暗号化バックアップ | オフライン媒体（§4.4） | 秘密（暗号化済み） |

- **`epoch`**: Share の世代。Refresh / Resharing のたびに増加する。`Y` と `key_version` は Refresh / Resharing では変わらない。
- **`key_version`**: Key Rotation で増加する。暗号文ヘッダに記録するため、復号時にどの鍵世代かを判別できる。
- 部分復号要求には `key_id`・`epoch` を含め、**現在の epoch と一致しないノードは応答しない**（古い Share が混入しても `d` を壊さないための安全弁）。
- ノードの状態（既存の `LOCKED` / `ACTIVE` / `INVALIDATED`）に、鍵まわりの補助状態を追加することを提案する。

| 補助状態 | 意味 |
|---|---|
| `SHARE_SEALED` | Share が暗号化保存のままメモリに未ロード（`LOCKED` と対応） |
| `SHARE_LOADED` | Share をメモリにロード済み（`ACTIVE` と対応） |
| `SHARE_STALE` | epoch が古い。Resharing による再同期待ち（部分復号を返さない） |
| `RESHARING` / `KEYGEN` | 儀式の実行中（部分復号は中断せず旧 epoch で継続できるが、コミットで原子的に切替） |

### 4.1 初期化: 鍵生成 → Share 分割 → 配布（DKG フロー）

前提: 3 ノードがすべて稼働・相互認証済み（mTLS + TPM）。鍵生成は最も特権的な操作のため、**3-of-5 端末承認による明示的な認可**を条件とする。

```
フェーズ1  Pedersen VSS で配布（情報理論的に秘匿）
  各ノード i:  f_i(x) = a_i0 + a_i1·x,  f'_i(x) = b_i0 + b_i1·x  を CSPRNG で生成
               C_ik = a_ik·G + b_ik·H  (k=0,1) を Raft ログへ公開
               (f_i(j), f'_i(j)) を ノード j へ 1対1 送付
               （mTLS に加え、宛先ノードの公開鍵で HPKE 暗号化。Raft/中継に平文を載せない）
  各ノード j:  f_i(j)·G + f'_i(j)·H = Σ_k j^k · C_ik を検証
               不一致なら苦情（complaint）を Raft に記録 → 該当 i を失格（QUAL から除外）

フェーズ2  Feldman コミットメントで公開鍵を抽出
  各ノード i ∈ QUAL:  A_ik = a_ik·G  (k=0,1) を公開
  各ノード j:  f_i(j)·G = Σ_k j^k · A_ik を検証
               不一致なら、他の正常ノードの Share から f_i を再構成して A_i を公開
  出力:  Share  s_j = Σ_{i∈QUAL} f_i(j)
         公開鍵  Y   = Σ_{i∈QUAL} A_i0
         公開Share Y_j = Σ_{i∈QUAL} (A_i0 + j·A_i1)

フェーズ3  鍵確認（Known-Answer Test）
  ランダムなテストメッセージを Y 宛に HPKE 暗号化し、
  3 通りの全ペア {A,B}, {A,C}, {B,C} で閾値復号 → 全ペアで一致することを確認
  成功したら Raft に (key_id, Y, Y_j, C_k, epoch=1) をコミット

フェーズ4  永続化とバックアップ
  各ノードは Share を TPM 封印鍵で暗号化して保存（暗号化保存後、平文を即ゼロ化）
  暗号化バックアップを作成（§4.4）
```

- ラウンド数は概ね 3〜4（各ラウンドは Raft コミットを伴う）。儀式は稀で、所要時間は秒〜数十秒の範囲で問題ない。
- 失格者がいても n=3 では 1 台までは継続できる（残り 2 台が正常 Share から f_i を再構成する）。2 台が不正な場合は中止し、最初からやり直す。
- **MVP の暫定手順**: DKG の実装が間に合わない場合のみ、エアギャップした端末で Dealer が `d` を生成し (2,3) Feldman 分割して 3 ノードへ配布し、直後に Dealer 側の `d` と Share を完全消去する。この場合、Dealer が `d` を一時的に知るため最終形では採用しない。
- 初期化後、`qorynth-seal` は `Y` を取得し、OpenBao の初期化時に root key をクォーラム不要の公開鍵暗号化（HPKE）でラップする。

### 4.2 運用中: 2-of-3 クォーラムで復号して Unseal Key Part を返却

```
OpenBao ──(Unwrap要求: key_id, 暗号文 (R, ct), purpose)──► qorynth-seal
  qorynth-seal:  ① OpenBao 側の認証（mTLS・許可リスト）
                 ② 要求ごとに request_id を生成
                 ③ ノード A, B, C のうち応答の速い 2 台を使う
                   （最初から 3 台へ並列送信し、検証を通った先着 2 つを採用 = ヘッジ要求）
  qorynth-node:  ① 認可チェック: 呼び出し元が seal ロールか / 失効していないか
                 ② クラスタ状態 ACTIVE か / 自ノードが SHARE_LOADED か
                 ③ key_id / epoch が現行か、R が有効な曲線点か
                 ④ レート制限・用途（purpose）許可リストの検査
                 ⑤ D_i = s_i · R と DLEQ 証明 π_i を計算して返す
                 ⑥ 監査ログ（要求元・key_id・時刻）を追記
  qorynth-seal:  π_i を検証 → Lagrange 合成 → HPKE 鍵導出 → AES-256-GCM 復号
  qorynth-seal ──(平文の Unseal Key Part)──► OpenBao   ※TLS 1.3、復号結果は使用後ゼロ化
```

- 不正な部分値（DLEQ 検証失敗）を返したノードは特定でき、他の 1 台と第 3 のノードで再試行する。不正を理由にノードを `INVALIDATED` にするかは運用判断（誤検知による可用性低下とのトレードオフ）。
- `ACTIVE` でない（`LOCKED`）ノードは部分復号を返さない。

### 4.3 ノード失効: 失効ノードの Share を無効化し、残り2台＋新規1台で再シェアリング

想定: ノード C が盗難・侵害の疑い。残るノード A, B は正常。

```
手順
 0. 認可     3-of-5 端末承認で「ノード C の失効と Resharing」を承認
 1. 隔離     Raft で C を INVALIDATED にする。C の mTLS 証明書を失効させ、TPM の ID を拒否リストへ
            （他ノードは C からの接続・要求を以後拒否。これが実効的な遮断）
 2. 新ノード D を登録（TPM ID 生成・mTLS 証明書発行・ノード公開鍵の登録）
 3. VSR      旧委員会のうち t=2 台（A, B）が「配布者」となる
              各配布者 i ∈ {A,B}:
                h_i(x) = s_i + e_i·x  （h_i(0) = s_i となる 1 次式）を新規生成
                h_i の係数に対するコミットメント E_ik = (係数)·G を公開
                検証: E_i0 が旧コミットメントから導いた Y_i と一致すること（改ざん防止）
                h_i(j) を 新委員会 j ∈ {A', B', D} へ 1対1 暗号化送付
              各受信者 j:
                h_i(j)·G = Σ_k j^k · E_ik を検証
                新 Share  s'_j = Σ_{i∈{A,B}} λ_i · h_i(j)
                         （λ_i は集合 {A,B} の Lagrange 係数）
              新しい多項式 f'(x) = Σ_i λ_i · h_i(x) は f'(0) = Σ λ_i s_i = d、
              よって公開鍵 Y は不変。新コミットメントは E から導出する
 4. 確認     新 Share のみで全ペア（{A',B'}, {A',D}, {B',D}）の KAT 復号に成功すること
 5. コミット  Raft に epoch+1 とコミットメントを書込み、全ノード一斉に切替
              （切替前は新 Share を仮置きし、失敗時は旧 epoch でロールバック）
 6. 消去     A, B は旧 Share を安全消去（上書き・ゼロ化）。旧 epoch のバックアップを失効
 7. 再バックアップ  新 epoch の暗号化バックアップを作成（§4.4）
```

**判断ポイント:**

- **盗難された C の旧 Share は、単独では無害**（1 Share は情報を与えない）。危険なのは、攻撃者が **旧 epoch の別の Share を 1 つ追加で入手する**ことである。Resharing 後に A, B が旧 Share を消去し、旧バックアップを失効させる理由はここにある。
- **Key Rotation の併用基準**: 次のいずれかに該当する場合は、新しい DKG で新しい `d`・`key_version` を作り、OpenBao の root key を新鍵で rewrap する。
  - 旧 Share が 2 つ以上、攻撃者に渡った可能性がある（2 ノード盗難を含む）
  - 旧世代の Share を含むバックアップの漏洩が疑われる
  - 盗難ノードが `ACTIVE` のまま長時間オンラインで放置されていた
  - 定期ローテーション（運用ポリシーで決める）
- 暗号化はクォーラム不要の公開操作のため、rewrap は「旧鍵で 2-of-3 復号 → 新 `Y` で再暗号化」で実現できる。OpenBao 側で root key をどう再ラップするか（Seal の Rewrap / Seal migration の可否）は §6 で確認する。
- **スペア端末がない場合**: A, B のみで 2-of-2 に一旦 Resharing して C の旧 Share を無効化し（可用性は下がる）、D の調達後に (2,3) へ再度 Resharing する。
- **2 ノードが同時に失効した場合**: 残り 1 台は配布者になれない（配布者は t=2 台必要）。バックアップの Share を 1 つ復旧して配布者を 2 台にそろえるか、Key Rotation（新規 DKG ＋ 旧鍵での rewrap 後に旧鍵廃棄）で対処する。

### 4.4 バックアップ: 鍵 Share の暗号化バックアップと復旧フロー

**設計原則:** バックアップは「閾値 2」を破らない構造にする。3 つの Share を同じパスフレーズで暗号化して同じ場所に置くと、実質 1-of-1 に退化する。

| 項目 | 方針 |
|---|---|
| 単位 | **Share ごと**に暗号化する（`s_i` + 公開メタデータ `key_id`・`epoch`・コミットメントのハッシュ） |
| 暗号化先 | Share ごとに**別の復旧用公開鍵**（HPKE / age 形式など）を使う。復旧用秘密鍵は **別々の管理者・別々のオフライン媒体**（ハードウェアトークン等）に保管する |
| 保管場所 | 暗号化バックアップはノードと**別の場所**に分散。復旧用秘密鍵とは別に保管 |
| 世代管理 | **同時に有効な epoch は 1 つだけ**。Refresh / Resharing の後は旧 epoch のバックアップを失効（可能なら復旧用鍵も更新）。旧 epoch の Share を 2 つ集められると `d` が復元できるため |
| 完全性 | 復旧時に `Y_i`（公開Share）と照合し、バックアップが正しい Share か検証する |

復旧フロー:

| 失われたノード数 | 復旧方法 |
|---|---|
| 1 台 | バックアップ不要。残り 2 台から Resharing で新ノードに Share を再発行（§4.3） |
| 2 台 | 残る 1 台 + バックアップの Share を 1 つ復旧して配布者 2 台を確保 → Resharing で 3 台に戻す |
| 3 台 | バックアップの Share を 2 つ復旧（2 名の復旧管理者が必要）→ 新ノードへ Resharing。復旧中に `d` を再構成する手順は避け、Share を新ノードへ直接ロードして VSR を行う |
| バックアップも 2 つ以上喪失 | `d` は復元不能。新規 DKG で新しい `key_version` を作る。OpenBao は旧 root key を復号できないため、**OpenBao 側のリカバリー（recovery key / 再初期化）に依存する**ことを運用手順に明記 |

### 4.5 全台再起動: LOCKED 移行、再承認、Share の再同期

```
全台停止 → 電源投入
  各ノード:  起動 → LOCKED（SHARE_SEALED）。Share は暗号化されたまま、メモリへロードしない
             Raft に参加し、クラスタ状態（key_id・epoch・コミットメントのハッシュ）を取得
  承認:      登録端末 3-of-5 が有効化を承認（WebAuthn / Passkey）→ 承認証明書を発行
  有効化:    各ノードが承認証明書を検証 → TPM 封印鍵で Share を復号してメモリへロード
             Y_i との整合性を確認 → SHARE_LOADED / ACTIVE
  再同期:    自ノードの epoch がクラスタより古い場合は SHARE_STALE。
             部分復号を返さず、Resharing による再発行を要求（旧 Share は破棄）
```

- **LOCKED の効力の確保**: Share をロードする鍵を保持する TPM の PCR ポリシーで、**承認検証を行うソフトウェアが測定された状態**でしか封印が解けないようにする（承認なしにロードするコードを起動できない）。これは暗号的な強制ではなくポリシーによる強制であり、強化案は §6 に記す。
- Share のローカル復号鍵は暗号化保存の保護であり、**1 ノード盗難への防御は閾値そのもの**で担保する（TPM だけに頼らない。§5.1）。
- **1 台だけ再起動した場合**（既存資料で未確定）: 本書の推奨は「クラスタが `ACTIVE` で、再起動ノードが測定起動と mTLS/TPM 認証を通過し、epoch が一致するなら、再承認なしで Share を再ロードして復帰」。ただし盗難ノードが元のネットワークに接続した場合のリスクがあり、最終判断は承認・メンバーシップ設計（フェーズ2〜4）と合わせて行う（§6）。
- 停止中に Refresh が行われた場合の再同期: 配布者は停止ノード宛の sub-share を暗号化して保持し、復帰時に配布する（停止ノードが戻ってから新 Share を計算できる）。

## 5. 脅威モデルとの整合性確認

前提の共通事項: 部分復号の要求は `qorynth-seal` のみが発行でき、ノード同士は Share を送らない。Qorynth ノードの電源が落ちている間、Share は暗号化されている。

### 5.1 Qorynth ノード 1 台 + OpenBao ノード 1 台の盗難 → Seal 鍵を復号できない（**要件を満たす**）

| 攻撃者が持つもの | 内容 |
|---|---|
| Qorynth ノード側 | Share `s_i` が 1 つ（TPM 封印の暗号化状態、または最悪平文）。公開コミットメント |
| OpenBao ノード側 | ラップ済み root key（HPKE 暗号文 `(R, ct)`）、OpenBao の mTLS 資格情報 |

- **オフライン解析:** 1 Share だけでは `d` に関する情報が得られない（Shamir の性質）。Qorynth ノードの TPM を突破できたとしても結果は変わらないため、盗難防御は TPM ではなく**閾値の性質**に依拠する。`d` が得られないのでラップ済み root key は復号できない。**要件を満たす。**
- **オンライン攻撃（盗難機器をネットワークに接続）:** 盗難した OpenBao ノードの資格情報で `qorynth-seal` に Unwrap を要求する経路が残る（Auto-Unseal の性質として、認証された OpenBao ノードは Unseal できる）。防壁は、①クラスタが `LOCKED` なら応答しない、②`qorynth-seal` の許可リスト・接続元ネットワーク制限・レート制限・異常検知、③盗難直後の資格情報失効と §4.3 のノード失効、である。これは本プロトコルの範囲外の運用要件として明記する。
- 盗難した Qorynth ノードを元のネットワークに接続しても、部分復号を要求できるのは `seal` ロールだけなので、他ノードから Share は得られない。ノード自体は `INVALIDATED` にして遮断する。

### 5.2 Qorynth ノード 2 台の盗難 → 鍵復号が可能（**設計上限**）

- 2 つの Share から `d` を復元できる。ラップ済み root key も入手していれば復号可能。
- これは (2,3) 方式の定義上の限界であり、設計の欠陥ではない。
- 対応: 2 台同時盗難は「`d` 漏洩」とみなし、**Key Rotation（新 DKG・旧鍵からの rewrap）＋ OpenBao の root key rekey** を実施する。盗難前に取得された暗号文は保護できない点を運用手順に記載する。
- 緩和: Share の暗号化保存・TPM 封印・承認ポリシーによって攻撃者の作業コストと時間を上げ、検知と失効までの猶予を稼ぐ（防御の層であり、閾値の代替ではない）。

### 5.3 承認端末 3 台の盗難 → 有効化のみ可能、鍵復号は不可（**要件を満たす**）

- 承認端末は Share を持たず、承認は鍵処理と独立している。3 台の承認で `LOCKED → ACTIVE` にはできても、`d` は得られない。
- 攻撃者がさらにクラスタへ到達し、seal 資格情報も持つ場合は復号を要求できる。したがって承認端末の WebAuthn は **User Verification（PIN・生体）を必須**にし、盗難を検知したら端末を失効させる。
- 注意点（承認設計側の課題）: 5 台のうち 3 台が盗難されると、攻撃者が承認端末集合の変更自体を承認できてしまう。端末集合の変更（登録・失効）には通常の有効化承認より高い基準（例: 4-of-5 や別系統のオフライン管理鍵）を設けることを、フェーズ3で検討する。

### 5.4 Signaling 停止 → 接続は継続可能（**要件を満たす**）

- 復号（部分復号の送受信）は `qorynth-seal` ↔ `qorynth-node` の QUIC 直接接続のみで行い、Signaling を使わない。既知の Peer（アドレス・証明書）が保持されていれば復号は継続できる。
- 影響を受けるもの: 新ノード登録（Resharing の新ノード D）や、アドレス変更・NAT マッピング失効後の再接続。Resharing を行う場合は、Signaling 停止中も既知アドレスで直接通信できることを確認する。
- Raft による状態同期とコミットメントの公開は Signaling に依存しない。

### 5.5 追加シナリオ

| シナリオ | 結果 |
|---|---|
| Qorynth ノード 1 台の実行時侵害（ソフトウェア的） | 閾値 HPKE 復号では、侵害ノードは自分の Share しか得られず、他ノードは `seal` ロール以外へ部分値を返さない。**再合成方式では守れないケースで、本方式を選ぶ主因**。ただし侵害ノードは自分の Share を持ち出せるため、失効と Resharing（必要なら Key Rotation）を実施する |
| `qorynth-seal` の侵害 | 稼働中に侵害された場合、攻撃者は復号を要求でき、各暗号文ごとの `S = d·R` を得る。長期鍵 `d` は得られない。レート制限・監査・用途制限で被害範囲を狭める。`qorynth-seal` は 2 台構成のため、侵害側を失効して継続する |
| 1 台停止 + 1 台が不正な部分値を返す | 正常なノードが 1 台しか残らず閾値 2 に届かないため**復号は不可**（可用性の限界）。ただし DLEQ 検証で不正ノードは特定でき、機密性は損なわれない。停止ノードの復帰、または不正ノードの失効と Resharing で回復する |
| ネットワーク分断（1 台が孤立） | 孤立ノードは Raft の多数派に入れず `ACTIVE` を維持できない。多数派の 2 台で復号を継続 |

### 6.2 性能・レイテンシの見積もり（QUIC 経由の分散復号）

**1 回の復号（運用中・§4.2）**

| 要素 | 見積もり | 備考 |
|---|---|---|
| ノードの計算 | 1 回のスカラー倍算 + DLEQ 証明生成でおおむね 1 ms 未満 | P-256 のスカラー倍算は数十〜百 μs 程度 |
| 合成役の計算 | DLEQ 検証 2 回 + スカラー倍算 2 回 + AES-GCM でおおむね 1 ms 未満 | |
| ネットワーク（確立済み接続） | **1 RTT**（`seal` → 2 台以上へ並列送信し、応答を待つ） | LAN で 1 ms 前後、拠点間 WAN で 10〜100 ms を想定 |
| 初回接続 | QUIC（TLS 1.3, mTLS 込み）で追加 **1 RTT**。計 2 RTT | 0-RTT は部分復号要求のリプレイを避けるため**使用しない** |
| 失敗時（ノード 1 台無応答） | ヘッジ要求（3 台へ並列送信し先着 2 つを採用）により追加遅延なし。ヘッジなしだとタイムアウト待ちが発生 | 接続キープアライブでタイムアウト検出を早める |
| TPM | 通常の復号経路では使用しない（Share は起動時に一度だけロード） | TPM 操作は数十〜数百 ms かかるため |

**結論:** 通常の復号は 1〜2 RTT + 数 ms。Auto-Unseal は OpenBao の起動時（および Seal のヘルスチェックの設定次第）にしか呼ばれないため、レイテンシは実用上問題にならない。

**儀式（頻度は稀）**

| 操作 | 概算 |
|---|---|
| DKG（GJKR New-DKG） | 3〜4 ラウンド、各ラウンドで Raft コミット（1 RTT + 永続化のため fsync）。合計で数百 ms〜数秒（ネットワーク条件次第） |
| Resharing（VSR） | 配布 → 検証/苦情 → KAT → コミットで 3〜4 ラウンド。同程度の数秒 |
| Refresh | 同上 |
| 将来の署名（参考） | FROST は 2 ラウンド（事前コミットで 1 ラウンド）、DKLs23 は 3 ラウンド |

実際の値は、拠点配置（ノード間の RTT）と Raft の永続化性能に依存するため、フェーズ5の最初にプロトタイプで計測して本節を更新する。
