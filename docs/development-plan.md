# 開発計画 — Qorynth

## 実装順序

### フェーズ1: P2P通信と冗長Signaling

**目標:** 3ノード間のP2P接続確立とSignalingサービスの冗長化

**タスク:**
- [ ] プロトタイピング: QUICベースのP2P接続
- [ ] Peer Discovery メカニズム（DNS-SD, mDNS, またはSignaling経由）
- [ ] NAT Traversal（STUN/TURNまたはhole punching）
- [ ] Signalingサーバーの実装（3ノード冗長化）
- [ ] Signaling間の状態同期

**検証:** 3ノードがNAT越しに相互接続できることを確認

### フェーズ2: ノード認証・メンバーシップ管理

**目標:** 信頼できるノードのみがクラスタに参加できる仕組み

**タスク:**
- [ ] mTLS証明書管理（自己署名CAの構築）
- [ ] TPM 2.0によるノードIDの生成・保持
- [ ] クラスタメンバーシップの追加/削除プロトコル
- [ ] メンバーシップ情報のRaftによる同期

**検証:** 不正なノードがクラスタ参加できないことを確認

### フェーズ3: 3-of-5端末承認

**目標:** HSM有効化に必要な複数端末承認の仕組み

**タスク:**
- [ ] 端末登録（WebAuthn/Passkey）
- [ ] 承認投票のプロトコル設計
- [ ] クォーラム判定ロジック
- [ ] 承認状態の永続化

**検証:** 3台未満では承認成立しない、4台以上で成立することを確認

### フェーズ4: HSM有効化状態管理

**目標:** クラスタ全体の有効化状態を管理

**タスク:**
- [ ] 状態遷移マシン（LOCKED / ACTIVE / INVALIDATED）
- [ ] ノード再起動時の状態復旧
- [ ] クォーラムに基づく状態決定
- [ ] フェイルオーバー時の状態一貫性

**検証:** ノード停止・再起動時の状態遷移が正しく動作することを確認

### フェーズ5: 閾値暗号による分散鍵処理

**目標:** 秘密鍵を分散保持し、2-of-3クォーラムで鍵処理

**タスク:**
- [ ] 閾値暗号プロトコルの選定と実装
- [ ] DKG（Distributed Key Generation）の実装
- [ ] 分散復号プロトコル
- [ ] 鍵Shareのローテーション

**検証:** 1台だけのノードでは復号できない、2台以上で復号できることを確認

**設計判断:** 閾値暗号方式の選定がこのフェーズのキーマイルストーン

### フェーズ6: OpenBao Auto-Unseal連携

**目標:** OpenBaoのAuto-UnsealをQorynth経由で実行

**タスク:**
- [ ] OpenBao Auto-Unsealプロトコルの調査
- [ ] Seal Gatewayの実装
- [ ] Unseal Key Partの取得・返却フロー
- [ ] OpenBaoとのエンドツーエンド統合テスト

**設計判断:** PKCS#11互換レイヤー vs 専用KMSプラグイン

### フェーズ7: 鍵バックアップ・復旧・盗難時失効

**目標:** 障害復旧とセキュリティインシデント対応

**タスク:**
- [ ] 鍵Shareの分散バックアップ
- [ ] バックアップからの復旧手順
- [ ] 盗難ノードの検知と失効
- [ ] 鍵Shareの更新（再シェアリング）

## 未決定事項のスケジュール

| 項目 | 決定時期 | 依存 |
|---|---|---|
| 言語・技術スタック | フェーズ1前 | 全体 |
| 閾値暗号プロトコル | フェーズ5前 | フェーズ4以降の設計に先行 |
| OpenBao連携方式 | フェーズ6前 | フェーズ5と並行して決定 |
| HSM実装（既製/TPM） | フェーズ5前 | 閾値暗号と連動 |
| NAT Traversal戦略 | フェーズ1内 | P2P実装と並行 |

## 初回リリースの範囲（MVP）

MVPでは以下を達成することを目指す:

1. 3ノード間のP2P接続
2. 2-of-3分散鍵保持（プロトタイプレベルの暗号）
3. OpenBao Auto-Unsealとの連携（単一Signaling）
4. 基本状態管理（LOCKED / ACTIVE）
